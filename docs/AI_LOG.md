|---|---|---|---|
| 1. 배경 조회 실행 시점 | 분석 단계에서 관리자 수동 실행 권장 | 실제 API 리턴 확인 후 결정하도록 보류 | 사용자 응답으로 제안을 즉시 확정하지 않았다. 당시 업무 POST는 비활성. 실측 이후 사용자가 수동 실행을 확정해 구현한 순서를 대화·코드와 대조 |

세 번째 항목은 실제 대화 원문을 확인한 사례로 교체했다. 이전 Thymeleaf 선택은 원문 미확인으로 제출 사례에서 제외하며 역사 기록에만 남긴다. 사용자 자신의 회원가입 아이디어 철회를 AI 제안 거절로 바꾸거나 가상 사례를 추가하지 않았다. 세 번째 사례의 근거는 실제 보류 사유·기본false·방침 변경이며, 사용자가 말하지 않은 개인적 동기를 추정하지 않는다.

## B. AI가 처음에 잘못 만들어 고친 지점

### 1. 퇴사 세션의 재직 검사 누락 — 테스트로 발견

초기 EmploymentGuardFilter는 `getServletPath()`만으로 API 경로를 판별했다. servletPath가 빈 요청에서는 재직 검사를 건너뛰어 퇴사 세션·재직 상태 변경 테스트2개가401 대신200으로 실패했다(당시14개 중2개). PathPatternRequestMatcher로 바꾸고 당시18개가 통과했다. 현재 백엔드 전체97개 검증과 최초 발견 시점의 수를 구분한다. 대상: `backend/src/main/java/com/bit/portal/auth/EmploymentGuardFilter.java`.

### 2. 중단 요청을 성공 지연으로 해석 — 실측·코드 대조로 발견

중단 경과10003.931728ms를 후보10001ms 초과 성공으로 해석한 부분을 수정했다. 중단 표본은 미확정으로 분리하고 실제 원본 회귀 테스트를 추가했다. 당시 프론트8개 통과. timeout 경과를 성공 응답이나 새 timeout의 성공률로 바꾸지 않는다.

### 3. Excel 원본 시각 정밀도 감소 — XLSX XML 대조로 발견

UTC ISO 문자열을 그대로 셀에 쓴 첫 내보내기에서 도구가 날짜로 자동 변환해 소수점 정밀도를 줄였다. XLSX XML과 원본을 대조해 발견했다. `UTC ` 접두사로 원문 문자열을 보존하고65행의 시작·종료 시각·지연을 다시 검증했다. 원본 JSON은 수정하지 않았다.

### 4. 업무 이력 lease 시각 불일치 — DB 상태 테스트로 발견

Java의 나노초 lease 시각과 DB의 마이크로초 저장 정밀도가 달라 조건부 UPDATE가 일치하지 않았다. 정상DETAIL 후clear 갱신·오류 후poll_stopped 갱신 테스트2개가 실패했다. lease를 마이크로초로 맞춘 뒤 통과했다. 당시 전체95개가 통과했으며 이번 후속 검증에서97개로 늘었다.

**후속 테스트 조건 수정:** 최초 업무 테스트의150ms 제한, 이후1초 제한이 정상 생성 전제를 깨뜨릴 수 있었다. 후속15개 실행에서 동시 갱신 테스트가409로 실패했고 단독 실행은 통과했다. 정상 로컬 요청 제한을3초, 의도적 응답 유실 지연을4초, 로컬 polling 전체 제한을10초로 분리하고 정상 생성 전제도 명시했다. 최종97개 통과. 실패 원인을 특정 네트워크나 cold start로 단정하지 않았으며 운영30초 제한은 바꾸지 않았다.

## 실제 협업·검증 범위

사용자는 기존 저장소 유지, 관리자 직접 생성, 연락처만 수정, 세션+CSRF, 퇴사 세션 재직 확인, PrimeVue4.5.5, 수동 조회·최소 이력·ADMIN 열람·상세 미저장·이력 삭제 없음을 결정했다. AI는 소스·모의 검증·측정 도구·제출 문서를 작성했다. 운영 SQL·Railway 변수·설정 배포는 사용자가 수행했으며 AI가 브라우저에서 승인된 조회를 검증했다.

|---|---|---|
