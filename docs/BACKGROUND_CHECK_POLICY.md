# 업무 배경 조회 — 구현 정책과 실측 한계

2026-10-12. 사용자 요청으로 업무용 POST·이력 저장·타임아웃·재시도·폴링을 구현했다. 사용자 확정 업무 정책과 AI가 선택한 보수적 초기 설정을 구분한다. 이번 검증은 H2·루프백 모의 API이며 실제 외부 호출을 추가하지 않았다.

## 제출 시 설명할 근거의 한계

1. **POST 타임아웃 후 생성 여부 복구: 실제 외부 검증 n=0.** 실제 관측 POST8건은201 응답을 받았다. 전체 타임아웃8건·취소2건을 POST 응답 유실 복구 표본으로 바꾸지 않는다. 초기 중복 비교2쌍 모두 다른 checkId였고 이력 대조 성공은1/2쌍이므로 외부 멱등성을 가정하지 않는다. 생성 성공 후 응답만 유실된 상황은 이번 모의 API 회귀 검증으로 확인했으나 외부 API의 복구 성공률은 아니다.
2. **pending → 최종 상태 발견 n=0, 정확한 업무 처리시간 n=0.** POST8건 중 처음부터clear4·pending4였다. pending 관찰은 오류·타임아웃으로 끝났다. 따라서 완료시간 분포나 최적 폴링 간격·대기 상한을 산출하지 못했다. 처음부터clear인 응답을 pending 전환 성공으로 세지 않았다.
3. **재조회 최소 간격·결과 유효기간은 실측으로 판단 불가.** 반복 생성 관측은 여러 기록의 생성 여부를 보여줄 뿐, 결과가 언제까지 업무적으로 유효한지 보여주지 않는다. 신원·조회 범위 변화나 장기 유효성을 검증한 자료가 없다. 임의의 기간을 붙이지 않고 관리자의 명시적인 신규 조회로 처리한다.

표본 부족 때문에 모든 통계가 무효인 것은 아니다. 관측된 중복과 지연은 방어 설계의 근거로 사용하고, 회복률·업무 처리시간·재조회 기간의 근거로 확대 해석하지 않는다. 원본·표본·실행ID는 [MEASUREMENTS](MEASUREMENTS.md)와 [설정 근거](API_DECISION_EVIDENCE.md)에 연결했다.

## 적용한 초기 설정

| 설정 | 코드 기본값 | 이유와 한계 |
|---|---:|---|
| 연결 제한 | 5,000ms | 기존 실험 설정 유지. 연결 단계 실측 n=0으로 최적값 미확인 |
| 전체 요청 제한 | 30,000ms | E09 LIST 정상n=2 최대26,884.973ms, E11 LIST 정상n=3 최대27,108.368ms 수용. DETAIL 최적값 미확인 |
| 자동 GET 재시도 | 추가0회 | 실제 추가retry1건/회복0건(503→30초 대기→500). 회복 개선 근거가 없어 추가 부하를 줄임 |
| POST 재시도 | 항상0회 | 반복 POST 비교2쌍에서 별도ID 생성. 결과 불명일 때도 자동 재전송 금지 |
| GET 재시도 활성화 시 | 500/503만, 추가 최대1회, Fixed1,000ms | 지원 경로이며 기본은 비활성. 전송 오류/타임아웃·401·403·404·429·성공 응답 형식 오류는 재시도하지 않음 |
| Retry-After | 유효 헤더 우선, 없으면 본문retryAfter | 다음 시도는 `max(Fixed 간격, 대기 안내)`. 다음 요청 전체 제한을 확보하지 못하면 중단하며 대기 시간을 줄이지 않음 |
| 폴링 간격 | 응답 후5,000ms | 처리시간 n=0이므로 부하·발견 지연 절충을 위한 초기값. 최적 간격 아님 |
| 자동 관찰 상한 | 예약부터120,000ms / 최대24회 | 업무 완료시간 보장이 아닌 자원 상한. POST 시간도 포함하며 남은 시간으로 GET 제한을 줄임 |
| 업무 HTTP 동시성 | 인스턴스당1 | 임시 보호 한도. 다중 인스턴스 전체 동시성1 보장이나 실측 안전 상한은 아님 |

GET 추가 재시도R, 요청 제한T, Fixed대기b이면 논리 요청 예산은 `(R+1)T+Rb`다. 기본R=0이면30초다. R=1/T=30초/b=1초이면61초이며 안내 대기 때문에 다음30초를 확보할 수 없으면 재시도하지 않는다. 폴링은 이 예산과 전체120초의 남은 시간을 함께 제한한다. 이 식은 자원 상한 모형이며 회복률 예측이 아니다.

자동 폴링은 관리자 모달이 열린 동안만 실행한다. 모달 닫기·로그아웃은 후속 타이머를 중단한다. 이미 도착한 POST를 취소·재전송하지 않는다. 재진입 시 저장된 pending의 남은 예산만 사용한다. clear/flagged, 오류, 횟수·시간 초과에서는 중단한다. pending을 실패/특이사항 없음으로 바꾸지 않으며 이후 수동 결과 GET은 가능하다.

유효한 대기 안내는 next_poll_at에도 반영해 수동 결과 확인·결과 불명 대조가 조기 호출하지 않게 한다. 잘못된 Retry-After 헤더나1일 초과 안내는 축소하지 않고 INVALID_WAIT로 중단하며 설정 검토 전 해당 요청의 후속 호출도 차단한다. 1일은 회복 예상치가 아닌 비정상 입력의 구현 보호 범위다.

## 신규 조회·중복·결과 불명

- 기존 결과 GET과 신규 POST를 구분한다. clear/flagged 이후에는 관리자 확인을 받고 새 요청 번호로 생성한다. 임의의 유효기간·최소 재조회 간격은 두지 않는다.
- 요청UUID를 POST 전에 저장한다. 같은 번호가 다시 도착하면 기존 상태를 반환한다. UUID는 로컬 중복 억제용이며 외부 API의 멱등성 키가 아니다.
- 직원 행을 짧게 잠그고 DISPATCHING/UNKNOWN/pending을 확인한다. 다른 관리자의 새 요청도 차단한다. 외부 응답을 기다리는 동안 DB 트랜잭션·직원 잠금을 유지하지 않는다.
- POST201의 대상·checkId·상태를 확인하면 KNOWN이다. 완전한400/401/403은 REJECTED, 전송 시작 전 중단은 NOT_SENT다. 그 외5xx·타임아웃·전송 단절·비정상201은 UNKNOWN으로 보관한다. 재시작 후 오래된 DISPATCHING도 UNKNOWN으로 바꾸고 신규 생성을 막는다.
- UNKNOWN이면 같은 서버 키로 외부 목록을 읽고 관리자가 시각·대상을 대조해 기록을 선택한다. 서버가 DETAIL의 employeeId/checkId를 확인하고 연결 행위를 기록한다. 자동 생성 여부 증명이나 exactly-once 보장으로 설명하지 않는다.
- 빈 목록·목록 실패·404만으로 미생성을 확정하지 않는다. 확인할 수 없으면 UNKNOWN을 유지한다. 수동 연결은 잘못된 기록을 선택할 수 있어 관리자 확인이 필요하다. pending 완료 없이 임의로 신규 생성 제한을 해제하는 API는 제공하지 않는다.

## 이력과 권한

V5의 background_checks는 요청UUID·사번·요청 계정ID·조회시각·checkId·상태·관찰시각·최소 전송/폴링 메타데이터만 저장한다. 특이사항은clear=없음, flagged=있음/검토 필요, 나머지=미확정으로 표시한다. background_check_views는 수동 결과 열람·관리자 연결 계정과 시각·상태를 남긴다. 성·이름·생년월일 입력, 키, 요청JSON, 범죄/학력/경력/신용 상세, 응답 본문은 두 테이블에 저장하지 않는다.

삭제·만료·정리 작업과 DELETE API는 없다. FK에 연쇄 삭제를 두지 않는다. 요청 목록은100건씩 조회하며 열람 이벤트 화면은최근100건을 표시한다. 표시 범위 밖의 기록도 DB에 남는다. 상세는 수동 확인 응답에서만 반환해 프론트 메모리에 표시하며 영구 브라우저 저장소에 넣지 않는다. 모달 닫기·로그아웃 시 지운다.

업무 API는 `/api/admin/**`로 ADMIN만 접근한다. POST 생성·갱신·연결은 CSRF를 요구한다. 일반 직원은 본인 대상이어도 이력·상세를 열람할 수 없다. 기존 외부 상세 GET도 저장 활성화 시 로컬 이력에 연결된 결과만 열람하고 계정을 기록한다.

## 운영 적용 — 미수행

1. V1/V3 테이블과 V5 미적용 여부를 확인한 뒤 [V5 SQL](../backend/src/main/resources/db/migration/V5__background_check_history.sql)을 트랜잭션으로 적용한다. 직원10명·계정을 삭제하거나 재초기화하지 않는다.
2. V5 적용 후 Railway에 `BG_RECORDING_ENABLED=true`를 추가한다. 기본false는 새 SQL 없이 기존 배포를 유지하기 위한 보호다. 기존 BG_ENABLED/BG_EXTERNAL_ENABLED와 서버 X_CANDIDATE_KEY도 확인한다.
3. 기존 timeout 환경변수가 있으면 기본값보다 우선한다. 아래 초기값으로 맞출지 운영 적용 전에 확인한다.
4. main 푸시는 자동 배포다. 이번 구현은 운영 SQL·환경변수·푸시·외부 호출을 수행하지 않았다. 추가 외부 검증은 별도 확인한다.

```yaml
background-check:
  recording-enabled: ${BG_RECORDING_ENABLED:false}
  client:
    connect-timeout-ms: ${BG_CONNECT_TIMEOUT_MS:5000}
    request-timeout-ms: ${BG_REQUEST_TIMEOUT_MS:30000}
  policy:
    max-retries: ${BG_MAX_RETRIES:0}
    retry-backoff-ms: ${BG_RETRY_BACKOFF_MS:1000}
    polling-interval-ms: ${BG_POLLING_INTERVAL_MS:5000}
    polling-max-duration-ms: ${BG_POLLING_MAX_DURATION_MS:120000}
    polling-max-attempts: ${BG_POLLING_MAX_ATTEMPTS:24}
```

검증 결과는 [SUBMISSION](SUBMISSION.md)에 기록한다. PostgreSQL·Railway의 새 업무 흐름과 실제 브라우저 동작은 아직 미검증이며 UI 빌드를 운영 확인으로 대체하지 않는다.
