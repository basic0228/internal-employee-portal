# 케이스별 100건 실험 계획 — 실행 전 검토 초안

사용자 확정: GET과 POST를 함께 설계, 서버 DB 자동 저장, **케이스당 모든 HTTP 요청을 합쳐 100건**. Polling과 중복 POST를 모두 포함한다. 이 문서는 호출 계획이며 운영 설정 결정은 아니다. `DECISIONS.md`의 최종 정책은 TODO다.

## 1. 첫 실험 범위

| 케이스 | 외부 요청 | 조건 | 목표 HTTP n | 지금 확보한 이 계획의 외부 표본 |
|---|---|---|---:|---:|
| G10-C1/C2/C3 | 같은 가상 사번 이력 GET | 요청 제한 10초, 고정 동시성 1/2/3 | 각각 100 | 각각 0 |
| G30-C1/C2/C3 | 같은 가상 사번 이력 GET | 요청 제한 30초, 고정 동시성 1/2/3 | 각각 100 | 각각 0 |
| G60-C1/C2/C3 | 같은 가상 사번 이력 GET | 요청 제한 60초, 고정 동시성 1/2/3 | 각각 100 | 각각 0 |
| P-POLL | POST 후 같은 checkId 상세 GET | 순차, 요청 제한 30초, 응답 수신 후 5초 대기, 추가 GET 최대 5 | 100 | 0 |
| D-DUP | 이력 GET → POST → POST → 이력 GET | 같은 사번·성·이름·생년월일, POST 사이 2초, 순차, 요청 제한 30초 | 100 | 0 |

11케이스의 외부 HTTP 총 목표 상한은 1,100건이다. 실패·타임아웃도 전송되어 관측된 HTTP 시도 1건으로 집계한다. 미시행 요청은 표본이 아니다. 이전 별도 GET 계획의 실제 3건/미시행 97건은 이 새 계획에 자동 편입하지 않는다.

공통 측정 조건: 연결 제한 5초, 요청 묶음 및 차수 사이 설정 대기 2초, 차수 최대 120초, 차수 최대 HTTP 20건/동시성 3. 화면은 보통 GET 차수당 최대 6건을 요청 제한과 동시성에 맞춰 줄인다. 마지막 묶음의 실제 폭(groupWidth)도 기록한다. 단일 프로세스에서 실험 1개만 실행한다. 여러 인스턴스 전체의 동시 외부 호출 제한은 별도 검증이 필요하다.

5초/2초/120초는 **초기 소규모 관찰을 위한 측정 후보와 상한**이다. POST 업무 처리시간 표본은 아직 0이므로 최적값·운영 추천값이라고 주장하지 않는다. 모든 케이스를 6시간 안에 마칠 수 있다고 보장하지 않는다. 먼저 GET 동시성 1과 POST 각 절차의 소규모 관측을 검토하고, 이상이 없을 때 케이스별 목표까지 진행한다. 503 회복 실패가 있었으므로 처음부터 1,100건을 일괄 실행하지 않는다.

## 2. Polling 절차와 해석

1. Polling 전용 가상 사번으로 POST 1건. 가상 성·이름·생년월일을 명시적으로 입력한다.
2. 201과 유효 checkId/status를 확인한다. 즉시 clear/flagged면 종료하고 **즉시 완료 코호트**로 구분한다.
3. pending이면 응답 완료 후 5초를 기다리고 해당 checkId의 DETAIL GET을 보낸다. 따라서 실제 시작 간격은 `이전 HTTP 경과시간 + 설정 대기`이며 고정 시계 주기라고 주장하지 않는다.
4. clear/flagged 발견, 추가 GET 상한, 전체 차수 deadline, 오류 또는 사용자 중단에서 종료한다. pending 종료는 CENSORED로 기록하고 완료시간을 만들어 넣지 않는다. 미완료 차수 후 새로운 POST를 자동 시작하지 않는다.
5. 관측 POST+GET 건수만 목표 100에 누적한다. 예: POST 1+GET 3이면 HTTP n=4, 업무 조회 n=1이다. 종료가 빨라도 GET 5건을 억지로 채우지 않는다.
6. 마지막 잔여 예산에 맞춰 최대 추가 GET을 줄인다. 예산이 1이면 POST만 관찰하고 pending은 미완료로 종료한다. 줄인 maxPolls는 원본 조건에 남으며 계획의 maxPolls와 비교해야 한다.

기록: POST 최초 상태, check 별칭, 각 GET 상태/시각/HTTP 경과시간, first/last pending 관측, 최초 최종 상태 관측, 외부 createdAt/completedAt, 중단 사유. 서버 업무 처리시간과 HTTP 응답시간을 구분한다. 완료 시각이 없으면 pending 마지막 관측~최종 발견 사이의 관찰 한계를 설명하고 정확한 완료시간을 대체 생성하지 않는다.

후보 분석은 5/10/15초 등의 주기에 대해 완료 시각이 있는 표본만으로 조회 수·발견 지연 모델을 비교한다. HTTP 지연·실패를 생략하는 모델의 가정을 표시한다. 실제 주기별 성공률·오류율을 입증하려면 해당 주기의 별도 실험이 필요하다.

## 3. 중복 POST 절차와 해석

1. 중복 전용 가상 사번의 LIST GET으로 기존 checkId 집합을 확인한다.
2. 같은 입력으로 POST, 응답 후 2초 대기, **의도한 중복 POST**를 1회 보낸다. 두 POST는 동일 요청 본문을 사용하며 타임아웃 재시도가 아니다.
3. LIST GET으로 이력을 다시 확인한다. 정상 전체 절차는 HTTP 4건(POST 2+GET 2)이므로 중단 없이 25묶음이면 100건이다. 신규 외부 기록 수가 반드시 50이라고 가정하지 않는다.
4. 반환 checkId 동일/상이, 각 HTTP 코드·status, 신규 이력 수, 반환 ID가 이력에 포함되는지를 기록한다. 실제 ID는 저장하지 않고 check 별칭만 저장한다.
5. POST 타임아웃·네트워크 오류는 `UNKNOWN_NO_REPOST`. 자동으로 POST를 다시 보내지 않는다. 허용된 잔여 예산에서 이력 관찰만 수행할 수 있으나 불명 POST와 새 이력의 인과관계를 단정하지 않는다. 다음 묶음은 중단한다.
6. 오류로 누적 수가 4의 배수가 아니면 마지막 예산이 1~3일 수 있다. 이때 잘린 절차는 `INCOMPLETE_BUDGET`으로 기록하고 완전한 중복 비교의 분모에서 제외한다. 실제 HTTP 표본으로는 유지한다.

이 케이스는 **2초 간격 동일 입력**의 동작을 측정한다. 첫 POST가 pending이었다고 해서 두 번째 POST 시점에도 pending이었다고 확정하지 않는다. pending 도중 중복과 완료 이후 중복을 엄밀히 분리하려면 중간 상세 GET을 포함하는 추가 프로토콜이 필요하다. 현재 표본으로 멱등성 보장·재시도 성공률·삭제 가능성을 가정하지 않는다.

## 4. 데이터 분리와 자동 저장

- GET 9조건은 같은 가상 사번을 사용한다. Polling과 중복은 각각 다른 가상 사번을 사용해 이력이 섞이지 않게 한다. 화면 기본 가상 사번은 계획 ID에서 생성한다. 실제 직원은 사용하지 않는다.
- 같은 키·가상 대상·버전·Endpoint·측정 조건을 유지해야 비교 가능하다. 키와 대상은 저장하지 않으므로 서버가 재개 시 동일함을 검증하지는 못한다. 변경되면 새 계획을 만든다. 결과를 해석할 때 실행 시각·차수·조건을 구분한다.
- `lab_campaigns`: 관리자 소유자, 계획 UUID, 조건과 HTTP 예산. `lab_runs`: 계획/케이스/차수 UUID, 상태, planned/observed, 정제된 원본 관측 JSON. 키·대상 ID·성명·생년월일·민감 상세·POST 본문은 저장하지 않는다.
- 실행 전 DB 행을 생성하고 관측을 브라우저에 알리기 전에 checkpoint 저장한다. DB 저장 실패는 다음 호출을 중단한다. 브라우저 연결 종료 시 다음 묶음을 막고 이미 시작한 묶음의 관측을 저장한다.
- 같은 관리자 계정으로 다른 PC에서 저장된 목록 및 분석을 불러올 수 있다. 다른 관리자 소유 데이터는 조회하지 못한다. 관리자 역할·세션·CSRF·퇴사 접근 통제는 기존 설정을 재사용한다.
- 새로고침 후 자동 호출은 없다. 키 재입력 및 명시적 실행이 필요하다. 재배포/프로세스 손실로 RUNNING이 남으면 실제 호출 수가 불명일 수 있어 재개를 차단한다. 저장된 관측 수는 보존하지만 관측되지 않은 실제 전송까지 알고 있다고 주장하지 않는다.
- 계획·모든 차수 JSON을 다운로드/텍스트 복사할 수 있다. 최근 실행 목록은 100차수 제한, 계획별 상세는 전체 차수를 조회한다. 판단 초안은 화면 내보내기가 필요하며 자동 저장 대상이 아니다.

## 5. 배포 및 미확정 작업

1. V4 SQL 검토 후 사용자 직접 운영 PostgreSQL에 적용. 기존 직원/계정 데이터 삭제 없음. H2 검증과 운영 PostgreSQL 적용 검증은 구분한다.
2. `LAB_RECORDING_ENABLED=true` 설정 후 배포. 기본값 false이므로 V4 전에는 기존 실험에 DB 저장을 강제하지 않는다. Dockerfile·운영 세션/쿠키/프록시 보안 설정 변경 없음.
3. 배포에서 저장 조회 확인 후 외부 실제 호출 계획을 확인받는다. 계획 저장은 부하 테스트가 아니다. POST 기록 삭제 API가 없으며 최대 POST 시도는 Polling 케이스 100건, 중복 케이스 50건(완전 절차만 진행할 때)이다. 최종 실제 생성 수는 응답으로 확인한다.
4. 최초 원본 관측을 검증한 후 차수별 목표까지 확대. 503/429/Retry-After, 오류·명세 불일치, pending 상한, 저장/연결 실패에서 중단한다. 사용자 재개는 별도 측정이며 자동 Retry 성공률로 집계하지 않는다.
5. 새로운 실제 데이터가 확보되면 케이스/조건별 Excel 집계를 추가한다. 기존 GET 전용 Excel은 새 POST·Polling 집계를 아직 지원하지 않으며 임의의 표본을 채우지 않는다.
