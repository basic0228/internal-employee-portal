# API Reliability Lab — 부족한 판단 근거를 채우는 추가 실험 설계

2026-10-12. 상태: **후속 Lab 구현 / 외부 미실행 / 운영 설정 미확정**. 아래는 계획 조건이며 실제 외부 관측이 아니다. 구현 범위와 검증은 문서 끝의 업데이트를 참고한다.

기존 [분석 근거](API_DECISION_EVIDENCE.md)의 11조건·34시도를 출발점으로 한다. 아래 숫자는 측정 결과가 아니라 **제안한 실험 조건과 최대 호출 예산**이다. 실험 설계 요청을 실제 외부 호출 승인으로 해석하지 않는다. 기존 캠페인의 100건 목표·원본·운영 설정은 변경하지 않는다.

## 1. 어떤 근거가 부족한가

| 결정 | 현재 부족한 근거 | 추가로 확인할 질문 |
|---|---|---|
| Retry 대상·횟수·간격 | 애플리케이션 retry n=0 | 초기 GET 실패 뒤 실제로 회복하는가? 회복에 추가 호출·대기가 얼마나 드는가? |
| Retry-After | 본문30초 n=2, 헤더 n=0 | 안내를 지킨 후 GET가 회복하는가? 남은 시간보다 안내가 길면 호출을 멈추는가? |
| Polling 간격·최대 대기 | 초기 pending n=2, 최종 발견 n=0 | 같은 조회가 언제 최종 상태로 보이는가? 예산 내 발견·미발견이 각각 몇 개인가? |
| 동시 요청 상한 | 서로 다른 시각의 작은 오류 중단 표본 | 동일 조건에서 동시성1/2/3의 정상 지연·오류·큐 대기·처리량이 달라지는가? |
| 전체 요청 제한 | 약27초 LIST 성공은 있지만 DETAIL 성공 n=2 | 유효한 LIST와 DETAIL의 긴 정상 응답을 어느 후보가 놓치는가? |
| 연결 제한 | DNS/TCP/TLS 단계 계측 n=0 | 새 Client와 재사용 Client의 총 시간 차이가 있는가? 연결 단계 자체를 계측할 수 있는가? |
| 예외·POST 결과 불명 | 실제500 내부 원인 불명, POST 결과 불명 복구 미검증 | 오류를 올바르게 구분하고 새 요청·중복 생성을 멈추는가? |

외부 성능은 실제 API에서 확인하고, 오류 분기·경계값·중단 로직은 로컬 모의 서버에서 확인한다. 로컬 테스트의 응답 시나리오를 외부 실측 데이터로 합치지 않는다. 보관30일·수동/자동 실행·권한 같은 업무 정책은 호출 횟수만 늘려서 확정할 수 없다.

## 2. 실행 전 공통 조건

- 서버에서 공통 BackgroundCheckClient를 사용한다. ADMIN·세션·CSRF·키 미저장 정책을 유지한다.
- 키·개인정보·응답 전문을 로그/DB/다운로드에 남기지 않는다. 실행ID, 익명 대상 별칭, 상태·시각·오류 분류 등 허용한 메타데이터만 저장한다.
- 단일 서버 인스턴스 여부, 다른 Lab 실행/업무 호출, Client revision·명세·키 스코프·대상·연결 모드를 확인한다. 미확인은 조건 불일치로 표시한다. 키 해시를 저장하여 비교하지 않는다.
- 첫 제안 보호값은 연결5초, 요청30초, **개별 실행 최대120초**, 서버 in-flight 상한3이다. T01/N01/R04의 요청60초는 별도 조건이다. 이 값들은 운영 권장값이 아니다.
- GET·POST·초기 요청·재시도·polling·대상 조회·오류·취소를 모두 실제 시작 시도 예산에 포함한다. 여러120초 실행의 누적 호출 예산도 별도로 제한한다.
- 401/404/계약 불일치, 저장 실패, 연결 종료, 사용자 중지에서 신규 호출을 멈춘다. 이미 보낸 요청의 외부 처리 취소를 보장하지 않는다.
- 일반 측정에서500/503/429/timeout을 만나면 중단한다. **R01/R02/R03/R04만 미리 정한 실패를 정해진 횟수 내에서 관찰하는 예외 실험**이다. 예외 허용은 해당 논리 작업에만 적용하고 일반 업무나 다른 캠페인에 확장하지 않는다.
- 503/429/대기 안내를 보면 부하 증가 실험은 멈춘다. 안내를 건너뛰거나 짧게 잘라 호출하지 않는다. 안내가 없는503에는 관측한30초를 임시 보호 대기로 제안하며 제공처의 보장으로 해석하지 않는다. 429는 로컬부터 검증하고 외부 유발 실험은 하지 않는다.
- 실측 전 전체 시간 상한과 HTTP 수를 검산한다. deadline 때문에 계획 수를 못 채우면 미실행으로 남긴다. 최종 상태를 얻으려고 POST를 계속 생성하지 않는다.

### B01/T01 — 실행 가능 상태와 지연 확인

같은 키와 유효한 가상 대상인지 확인하고 정상 응답의 계약 검사를 통과해야 후속 비교를 시작한다. 빈 이력의200도 정상 계약이면 기록하되 대상 이력 크기를 조건으로 남긴다. 선행POST를 만든 후에만 LIST를 호출해야 한다고 가정하지 않는다. DETAIL에는 실제 유효 checkId가 필요하다.

외부500은 허용한 error code/request ID가 있다면 최소 메타데이터로 수집하도록 검토한다. 응답 크기와 상태코드가 같다고 내부 원인이 같다고 판단하지 않는다. 이 조사는 B01/T01 관측을 재사용하며 별도 오류 유발 호출을 추가하지 않는다.

T01은 짧은 제한으로 일부러 정상 요청을 끊는 대신,60초까지 얻은 완료 지연을10/30/60초 후보로 오프라인 재분류한다. 후보에서의 실제 성공률과는 구분한다.60초 안에서도 미완료이면 응답 지연을60초로 채우지 않는다.

### R01 — GET500 회복과 대기 비교

실행 전에 대기2초/10초의 순서를 고정한다. 예를 들어 두 조건을 번갈아 배정하되 어느 조건이 먼저인지 기록한다. 오류가 생긴 뒤 좋아 보이는 조건으로 바꾸지 않는다. 각 논리 작업은 초기GET1회와, 초기500일 때에만 후속GET1회다.

각 작업의 요청 상한30초, 추가retry≤1, 전체120초, HTTP예산2다.500에 유효 대기 안내가 있으면 실제 대기는 `max(배정된 대기, 안내)`이며 실제 대기 구간으로 분리한다.503/429는 R01의 즉시 retry 대상으로 넣지 않고 과부하 중단으로 기록한다. 초기timeout/네트워크 오류도 R01의500 회복률에 섞지 않는다.

수집: 초기/후속 HTTP, attempt별retryIndex, 요청 지연, 예정/실제 대기, 대기 초과, 전체 논리 작업 경과, 예산 종료·미실행 이유. 최초3개 작업에500이 없으면 해당 조건의 적격 실패 표본n=0이다.500 표본을 확보하려고 호출 상한을 늘리지 않는다.

분석은 다음 분모를 모두 남긴다.

- 전체 논리 작업n: 배정한 조건에서 실제 시작한 작업 수.
- 적격 초기 실패n: 자연 발생한500 수.
- 후속 시작n, 예산 내 정상 발견n, 후속 실패n, 미실행/응답 불명n.
- **예산 내 관측 회복 비율** = 정상 후속을 확인한 작업 / 적격 초기 실패. 실제 재시도 표본이 있을 때만 계산한다. 미완료 작업은 따로 표시한다.
- 추가 호출 비용 = 후속 시도 수 / 전체 논리 작업 수. 전체 작업의 정상 발견 비율과 조건부 회복 비율을 구분한다.

두 대기의 초기 실패 유형·시각·실제 대기 안내가 다르면 숫자를 그대로 우열 비교하지 않는다. 이 탐색은 정책 내 회복을 기술하는 자료이며 retry 없는 대조군에 대한 인과적 개선을 증명하지 않는다.

### R02 —503와 대기 안내

유효 Retry-After는 초와 HTTP-date를 구분하고 수신 시각·파싱 결과·서버 Date가 있으면 함께 확인한다. 헤더 우선·본문fallback은 검토 정책으로 명시한다. HTTP-date의 시계 오차·과거/잘못된 값도 기록한다. [RFC 9110 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3).

초기503가 실제 발생하지 않으면 회복 표본n=0이다. 기존 측정의503를 새 초기 시도인 것처럼 재사용하지 않는다. 이전 실행에 연결한 단일 회복 확인은 `parentRunId`와 실제 경과를 남기고 신규 논리 작업과 구분한다. 원래 시도를 양쪽 실행의 HTTP수에 중복 집계하지 않는다.

필요한 대기와 다음 요청 상한이 남은 시간에 들어가지 않으면 `RETRY_DEFERRED_BUDGET`으로 끝내고 후속 시도0건으로 저장한다. 별도 창에서 나중에 회복 확인하려면 새 실행 조건·키 입력·연결 관계를 확인한다. 키를 저장한 장기 백그라운드 작업은 만들지 않는다.

### P01/P02 — 같은 조회의 최종 전환

P01은 새POST 없이 기존pending을 관찰하는 우선안이다. 기존 raw의 `check-1`만으로 실제checkId를 복구할 수 없으므로 LIST의 실제 대상과 checkId를 요청 중에 확인하고 동일 조회만 관찰해야 한다. 자동으로 이름·상태가 비슷한 이력을 이어 붙이지 않는다.

기존pending이 없으면 **P02: 가상 데이터POST1회→DETAIL최대6회**를 별도 승인하여 P01 대신 사용한다. HTTP상한은 동일하게7건, 외부 생성 시도는 최대1건이다. POST가 즉시clear/flagged이면 추가GET를 생략하고 즉시 최종 그룹으로 저장한다. pending이 나오지 않았다고 새POST를 계속 보내지 않는다. POST 결과 불명은 재전송하지 않는다.

기존pending P01은 선택 후 첫DETAIL을 바로 호출하고 이후 응답 후5초 기다린다. P02는 POST응답 후5초 기다린 뒤 첫DETAIL을 호출한다. 두 프로토콜의 경과 원점과 호출 수를 구분한다. deadline은 LIST/POST도 포함한 실행 전체120초다.6회GET 완료가 보장된다고 표시하지 않는다.

수집 항목은 `createdAt`, 유효한 `completedAt`이 있을 때의 값, 상태별 요청 시작/응답 종료, 최초pending·마지막pending·최초최종 관측, 정확한 서버 보고 업무 시간 또는 구간만의 관측, 최종 상태, 종료 이유다.

**완료시각이 없을 때 단일 완료시간을 만들지 않는다.** 마지막pending의 응답 수신부터 최초최종 수신 사이를 무조건 실제 전환 구간으로 쓰면 안 된다. pending 응답이 이동 중일 때 이미 상태가 바뀔 수 있다. 상태가pending→최종으로 단조롭게 전환하고 같은 서버 시계가 연속이라는 전제에서, 보수적인 로컬 시간 구간은 `[마지막pending 요청 시작, 최초최종 응답 종료]`로 둔다. 전제를 확인하지 못하면 상태 관측 순서만 보고한다.

유효한 `completedAt−createdAt`은 **외부 서버가 보고한 업무 시간**으로 분류하고 정밀도·시각 순서를 검증한다. 서로 다른 서버의 시각을 빼서 발견 지연을 확정하지 않는다. pending→최종 발견 시간은 관측 간격·HTTP지연을 포함하는 별도 지표다. 중도절단을 포함한 분석에는 사건 시각과 종료 가정이 필요하다. [NIST Kaplan–Meier 절차](https://www.itl.nist.gov/div898/handbook/apr/section2/apr215.htm).

| 2 | 2 | 3 | 1 | 3 |
| 3 | 3 | 1 | 2 | 3 |

각 수준을 독립120초 창에서 실행한다. 요청30초, 묶음 간 응답 후2초 대기, 수준 간30초 보호 대기를 제안한다. 오류·대기 안내가 있으면 해당 안내와 중단 조건이 우선이다. 추가 워밍업 호출은 기본0건이며 도입하면 예산에 포함한다.

동시성2의3건은2+1 묶음이므로 마지막1건을 완전히 포화된 동시성2 관측이라고 부르지 않는다. `configuredConcurrency`, `groupWidth`, 실제in-flight최댓값과 큐 대기를 같이 기록한다. 현재 러너의 record순서와 실제 응답 종료순서는 다를 수 있으므로 completion timestamp로 분석한다.

수준별 계획n=9와 실제n를 함께 표시한다. 정상/오류 지연·timeout·취소를 분리하고 블록 내 차이를 우선 본다. 정해진 순서가 시간 변화의 모든 영향을 제거하지는 않는다. 처리량은 해당 수준의 실제 경과를 분모로 정상 응답수/초와 전체 완료응답수/초를 나누고,2초대기가 포함된 총 경과와 대기 제외 경과를 구분한다. 이를 정상상태의 최대 처리능력으로 외삽하지 않는다.

오류가 생겨 뒤 수준을 못 실행하면 **불완전 블록**으로 남긴다. 운영 상한 선택 전에 사용자가 허용하는 오류/지연/대기 예산을 정해야 한다. 각9건만으로 '3이 안전하다'거나 '1만 안전하다'고 확정하지 않는다.

## 6. 수집 구조·통계·저장 연결

기존 `lab_campaigns`/`lab_runs`의 정제 JSON 저장을 유지하는 방향으로 검토한다. 저장 DTO의 허용 필드가 새 메타데이터를 보존하는지 먼저 확인한다. 이 설계에서는 SQL·보관 기간·기존 데이터를 변경하지 않는다.

추가 필드 초안:

- 설계 버전, caseId, blockId, blockOrder, 배정된 비교 조건, 실제 시작/미시행 수, 환경 확인 사항.
- logicalOperationId, parentRunId, 초기/후속 attemptId, retryIndex, 적격 실패 분류, 예정/실제 대기, 안내 출처, 잔여 시간·호출 예산, 종료 이유.
- 동일 업무 검증 여부, workflowId, 상대 요청/수신 monotonic 시각, 상태, 외부 보고 createdAt/completedAt의 유효성·정밀도, 관측 시간과 업무 시간의 구분.
- configuredConcurrency/groupWidth/실제 in-flight, 큐/HTTP/단계 경과, 비교 가능/불완전 블록 여부.

실제 checkId·사번은 요청 중 검증에만 사용하고 기존 저장 제외 정책을 유지한다. 익명 workflowId만으로 다른 실행의 동일 조회가 자동 검증되지는 않는다. P05에서 연결에 필요한 정보와 검증 방법을 구현하기 전에는 창을 합치지 않는다. 키 일치도 저장해 검증한 것처럼 표시하지 않는다.

Type7·표본 수·상태코드별 분모·정상/오류 분리·중도절단을 기존 분석과 동일하게 유지한다. 새 계획의100건 같은 숫자로 실제 n를 채우지 않는다. 중단으로 표본 수가 결과에 의존하면 고정 독립 표본의 검정/신뢰구간을 운영 회복률로 제시하지 않는다. 작은 표본을 일괄 무효로 버리지 않고 관측한 조건에서 확인한 회복·전환·비용과 해석 한계를 함께 쓴다.

현재 `campaign-evidence.mjs`는 **Retry OFF** 입력만 받는다. 새 retry 원본을 이 분석기로 억지로 집계하지 않고 논리 작업·attempt를 분리하는 새 분석 경로를 추가해야 한다. 기존34건과 새 회복 표본의 전체 p99/오류율을 합치지 않는다.

## 8. 진행 순서와 결과를 결정에 쓰는 방법

1. L01–L10 중 새 러너·중단·결과 불명 관련 로컬 검증부터 한다. 모의 원본은 LOCAL_MOCK으로 분리한다.
2. B01/T01으로 유효 대상·외부 정상 응답을 확인한다. 계속500/503이면 동시성 확대를 멈추고 원인을 조사한다. 이 경우 단일 R01/R02 진단의 재개는 별도의 제한된 계획으로 확인한다.
3. P01(필요시 승인된 P02)과 R01/R02를 소규모로 실행한다. 하나의120초 창이 끝났다고 정책을 확정하지 않는다.
4. 외부 상태가 허용할 때 C01을 진행한다. 부하 중단이면 뒤 조건은 미실행으로 보존한다.
5. 남은 불확실성에 맞춰 R03/P03/P05/C02/N01 등 필요한 후속만 선택한다. 남은 과제 시간을 확인하고 확장한다.
6. 각 실측 결과를 원본→조건별 Excel/MEASUREMENTS→DECISIONS 근거로 연결한다. 선정값·관련 runId·n·통계·이유·반대안·재검토 상황을 사용자가 확정한다.

## 9. Lab 반영 업데이트

- 계획 선택: B01/T01/R01/R02/P01/P02/C01 및 선택적 R03/R04/P04/C02. 가족별 별도 저장, 절차마다 명시적 실행, 조건·서버 상한은 고정한다. 새 SQL·환경변수·운영 업무 설정 변경 없음.
- 후속 절차는 한 번 실행하면 종료한다. HTTP 목표를 채우려고 조건부 재시도·POST를 반복하지 않는다. 실제 n와 미사용 최대 예산을 함께 표시한다. 재실행은 결과 검토 후 새 계획으로 수행한다.
- R01/R03은 정상 JSON으로 관측된 GET500, R02는 GET503, R04는 요청 timeout(이미 오류 HTTP를 관측한 경우 제외)만 대상이다. 401/404/429·계약 불일치·저장 실패·사용자 취소는 중단한다. R02 유효 안내 우선, 미관측 시30초 보호 대기; R01/R03/R04는 후보 대기와 유효 안내 중 큰 값. 안내+다음 요청 상한이 남은120초에 들어가지 않으면 후속0건이다.
- 원본: protocol/family/variant/block/order, 논리 작업, retryIndex, 예정/실제 대기, 안내 출처, 적격 초기 실패/후속 시작/회복/미실행 사유. 같은 Client를 재사용하고 일반 업무에는 retry를 추가하지 않는다.
- P01은 LIST에서 첫pending의 실제ID를 메모리에서만 사용한다. LIST의 pending 관측부터 같은 상세의 최종 발견까지 보존한다. 정확한 외부 완료시각이 없으면 생성하지 않는다. 보수적 전환 구간의 단조성 가정은 자동 검증된 사실이 아니다.
- C01/C02는 수준별3건, 3블록 순서를 서버에서 선행 완료로 검사한다. 선행 오류 뒤 다음 수준은 차단, 정상 수준 사이 최소30초. configuredConcurrency/groupWidth/Client 호출 겹침 최댓값/queue/시각을 보존한다. Client 겹침은 서버 내부 exchange 호출 기준이며 외부 wire 처리량·소켓 계측이 아니다.
- 분석: 실행별 정상/오류 분리, 논리 작업의 적격 실패 분모, 후속 미시행과 실제 회복을 구분한다. 새 원본의 CSV/Markdown은 retry metadata를 포함한다. 기존 Retry OFF 분석기에 새 retry 원본을 넣지 않는다.
- P03은 기존 오프라인 폴링 모델로 제공한다. P05의 창 간 동일 조회 검증과 N01의 창 간 Client 재사용 계측은 미구현이다. 화면에 사유를 표시하며 사용할 수 있는 케이스처럼 제공하지 않는다. 장기 대기 키 저장·타임아웃 뒤 POST 재전송은 하지 않는다.
