# DECISIONS.md — 설계 판단

2026-10-12. 과제의 네 판단 항목을 사용자와 확정한 정책에 맞춰 작성했다. 각 항목은 선택·이유·반대 장점·틀리는 상황으로 구성한다. 구현과 검증 범위는 [SUBMISSION](SUBMISSION.md), 기술 상세는 [BACKGROUND_CHECK_POLICY](BACKGROUND_CHECK_POLICY.md)에 있다.

## 1. 퇴사 시점과 접근 통제

- **선택:** 퇴사 커밋 후 다음 보호 API부터 차단. 만료 전 세션도 매번 DB 재직 상태를 확인하고 무효화한다.
- **이유:** 로그인 때의 인증이 현재 재직을 보장하지 않기 때문이다.
- **반대 장점:** 로그인 때만 검사하면 DB 조회 비용이 줄어든다.
- **틀리는 상황:** 퇴사자 증명서 열람이 필요하거나 조회 부하가 커지면 별도 권한·검사 방식을 검토한다. 실행 중 요청의 강제 취소는 제공하지 않는다.

## 2. Background Check 실행·재조회

- **선택:** 관리자 수동 실행. 완료 후 확인을 받아 재조회하고, pending·결과 불명은 새 POST를 차단한다.
- **이유:** 반복 POST 비교2쌍 모두 다른 ID가 생성돼 명시적 실행과 중복 제어가 필요하다.
- **반대 장점:** 가입 시 자동 조회하면 누락과 관리자 반복 작업을 줄인다.
- **틀리는 상황:** 전 직원 의무 조회·대량 처리에서는 자동화가 필요할 수 있다. 최소 재조회 간격·유효기간은 실측 근거가 없어 정하지 않았다.

## 3. 결과 보관·열람권한

- **선택:** 조회 시각·계정·대상·특이사항 상태 등 최소 이력만 보관. 상세는 저장하지 않고 ADMIN만 열람하며 이력은 삭제하지 않는다.
- **이유:** 조회 책임을 추적하면서 민감 상세의 로컬 복제를 줄인다.
- **반대 장점:** 상세 저장은 외부 장애 때 과거 내용을 재현하고, 기간 삭제는 저장량을 줄인다.
- **틀리는 상황:** 과거 상세 재현이 필수이거나 이력이 크게 늘면 보관 구조를 재검토한다. 30일 후보는 폐기했다.

## 4. 직원 본인 정보 수정

- **선택:** 이메일·전화번호만 즉시 수정하고 최종 수정 시각을 기록한다. 인사 필드는 보호한다.
- **이유:** 직원이 관리할 연락처와 이름·사번·재직·권한을 구분하고 API에서도 허용 필드만 받는다.
- **반대 장점:** 전체 정보 직접 수정은 관리자 정정 부담을 줄이고, 승인 방식은 변경을 사전 검토한다.
- **틀리는 상황:** 인적사항의 직접 정정이 필요하거나 연락처 승인·검증이 필요한 조직이라면 추가 절차가 필요하다.

## 이번 제출의 최종 선택값과 실측 한계

사용자의 업무 POST·이력 저장·설정 구현 요청으로 아래 기본값을 선택·적용했다. 사용자는 운영 검증 때 기본 정책 유지를 확인했다. 이번 제출의 선택은 완료했으며 **실측 최적성·장기 효과 검증은 TODO**다. [MEASUREMENTS 최종 선택표](MEASUREMENTS.md#10-최종-선택값과-코드-반영), [측정 실행 ID·통계·수학 모델](API_DECISION_EVIDENCE.md), [설정명·중단 조건](BACKGROUND_CHECK_POLICY.md)에 상세 근거를 연결했다.

| 항목 | 적용 초기값 | 근거와 남은 판단 |
|---|---|---|
| 연결 제한 | 5,000ms | 실험 설정 유지. 연결 단계 n=0, 최적값 TODO |
| 전체 요청 제한 | 30,000ms | E09 LIST 정상 n=2 최대26,884.973ms / E11 n=3 최대27,108.368ms 수용. DETAIL 최적값 TODO |
| GET 추가 retry | 0회 | R02 실제retry1건·회복0/1. 회복 보장 없이 부하를 늘리지 않음. 활성화 지원은500/503만 최대1회 |
| POST retry | 항상0회 | 중복 비교2쌍 별도ID, 실제 응답 유실 복구 n=0. UNKNOWN 보존·수동 연결 |
| Backoff·대기 안내 | GET retry 활성화 시 Fixed1,000ms / 유효 Retry-After 헤더 우선, 본문 대체 | Fixed/Exponential 실제 비교 n=0. 안내와 다음 요청 예산을 확보하지 못하면 중단 |
| 자동 polling | 응답 후5,000ms / 예약부터120,000ms / 최대24회 | Lab 최종 발견0·업무 수동 발견1·자동 발견0. 완료시간 추정이 아닌 자원 보호 초기값 |
| 업무 동시성 | 인스턴스당1 | 최신 C03 c1 n=3/오류1 이후 중단, c2/c3 n=0. 안전 상한·클러스터 전체 한도 아님 |

같은 로컬 요청UUID는 기존 이력을 반환하고 POST를 다시 보내지 않는다. 직원 잠금으로 pending/UNKNOWN을 예약 단계에서 검사하며 HTTP 대기 중 DB 잠금을 유지하지 않는다. clear/flagged·오류·시간/횟수 초과·모달 닫기·로그아웃은 자동 관찰을 중단한다. pending을 실패나 특이사항 없음으로 바꾸지 않는다. 이러한 선택은 외부 exactly-once 보장이 아니다.

## 함께 확정한 범위

PrimeVue4.5.5, 세션+CSRF, 관리자 직접 계정 생성만 제공, USER 연락처만 수정, 조회 모달에서 성·이름·생년월일을 명시 입력한다. 직원 원본 이름은 자동 분리하지 않고 동명이인·복성과 EMP-007 생년월일 NULL을 보존한다. SQL은 V1~V5 수동 적용이며 기존 데이터 삭제·비밀번호 재초기화를 하지 않는다. 회원가입·승인·MAC/IP 수집과 비밀번호 변경은 제공하지 않는다.
