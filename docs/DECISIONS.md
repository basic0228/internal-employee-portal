## 1. 퇴사 직원 접근 통제 — 확정, 로컬 검증

- **결정:** 퇴사 처리 커밋 후 다음 보호된 API 요청부터 차단한다. 세션에 저장된 계정 ID로 계정 활성 여부와 직원 재직 상태를 매번 DB에서 확인하며, 접근 불가이면 요청 세션을 무효화한다. 신규 로그인에서도 같은 재직 조건을 확인한다.
- **이유:** 만료 전 세션으로 퇴사자가 접근하면 재직 여부를 다시 판단하라는 사용자 요구를 반영했다. 세션의 과거 인증 상태만으로 현재 재직 여부를 판단하지 않는다.
- **반대 선택의 장점:** 로그인 시에만 검사하면 요청마다 발생하는 DB 조회를 줄일 수 있다. 세션 만료까지 제한된 접근을 제공하는 업무에도 사용할 수 있다.
- **이 선택이 틀리는 상황:** 퇴사자에게 증명서 등 일부 기능을 제공해야 하는 업무에서는 별도 권한이 필요하다. 대규모 트래픽에서는 요청마다 DB 조회하는 비용을 재검토해야 한다. 이미 실행 중인 요청의 강제 취소까지 제공하지 않는다.
- **검증:** Java 21 / H2 / MockMvc에서 기존 세션 2개 차단, 신규 로그인 차단, 계정을 활성 상태로 둔 재직 상태 변경, 컨텍스트 경로 처리 테스트 통과. DB 조회 실패는 503으로 접근을 허용하지 않는 단위 테스트 통과.
- **운영 검증:** TODO — 실제 PostgreSQL 및 Railway 환경.

## 4. 직원 본인 정보 수정 — 수정 범위 확정, 로컬 검증

- **결정:** 사용자 지시에 따라 연락처만 수정한다. 현재 연락처는 이메일·전화번호로 구성하며 저장 즉시 반영한다. 이름·생년월일·사번·재직 상태·권한은 수정 대상에서 제외한다.
- **이유:** 직원이 직접 관리할 수 있는 연락처와 인적사항·인사 정보를 구분한다. API도 연락처 두 필드만 받아 화면을 우회해 보호 필드를 수정할 수 없다.
- **반대 선택의 장점:** 이름·생년월일도 직접 수정하게 하면 관리자의 정정 업무가 줄어든다. 관리자 승인 방식은 변경을 사전 검토할 수 있다.
- **이 선택이 틀리는 상황:** 직원이 인적사항을 직접 정정해야 하거나 연락처에 조직 승인·검증 절차가 필요한 업무에서는 추가 흐름이 필요하다.
- **동작:** PUT /api/me/contact는 세션의 사번을 사용한다. 추가 본문 필드는 400으로 거절한다. 빈 연락처는 NULL로 저장하고 updated_at은 DB 시각으로 갱신한다. 기존 인사 데이터와 10명 시드는 변경하지 않는다.
- **동시 처리:** 연락처 저장과 퇴사 처리는 같은 직원 행을 잠근다. 퇴사가 먼저 커밋되면 저장을 거절하고, 저장이 먼저 실행되면 그 뒤 퇴사 처리한다. 이미 실행 중인 요청을 취소하는 방식은 아니다.
- **검증:** Java 21 / H2 / MockMvc 총 25개 테스트 통과. 소유권·보호 필드 거절·형식/길이·빈 값·CSRF·퇴사 세션·생년월일 NULL 보존 검증. 임시 H2 브라우저에서 이메일·전화번호 저장 후 새로고침으로 재조회했다.
- **운영 검증:** TODO — V3 PostgreSQL 적용, 운영 화면·동시 트랜잭션 검증. 별도 변경 이력 저장은 미구현.

## 5. 계정 생성 방식 — 사용자 확정

- **결정:** 관리자 직접 생성만 제공하고 생성된 직원 계정은 USER로 고정한다. 사용자 회원가입·관리자 가입 승인·MAC/IP 수집은 제외한다.
- **이유:** 과제의 관리자 계정 생성 기능에 집중한다. 추가 가입 업무 흐름과 브라우저 MAC 수집의 제약을 피한다.
- **반대 선택의 장점:** 가입 승인 방식은 사용자가 직접 정보를 입력하므로 관리자 입력 부담을 줄일 수 있다.
- **틀리는 상황:** 직원 규모가 커서 관리자가 계정을 직접 발급하기 어려운 경우에는 초대·승인 방식이 더 적합할 수 있다.
- **검증:** 관리자 생성, USER의 관리자 API 차단, 요청의 role=ADMIN 무시, 비밀번호 해시 저장, 중복 아이디 등록 롤백, 생년월일 NULL 시드 계정 연결 테스트 통과. 브라우저에서 생성된 직원 로그인 확인.

## 구현상 기본 처리 — 운영 정책 최종 확정과 구분

- 사번으로 직원을 식별한다. 동명이인은 허용한다.
- 시드 10명의 이름과 날짜를 그대로 유지하고 EMP-007은 NULL로 보존한다.
- 직원 생성과 계정 생성은 한 DB 트랜잭션이다. 기존 사번의 계정 발급은 인적사항이 일치하고 재직 중인 경우만 가능하다.
- 최초 관리자 부트스트랩은 직원에 연결하지 않는 계정이다. 기존 관리자 비밀번호는 재시작 시 바꾸지 않는다.
- 비밀번호는 BCrypt로 해시한다. 현재 검증은 최소 8자·UTF-8 72바이트 이하이다. 비밀번호 변경·초기 비밀번호 강제 변경은 미구현.
- 로컬 시연 계정과 H2 데이터는 테스트용이며 제출용 운영 계정이 아니다.
