# DECISIONS.md — API 실측 기반 설계 판단

2026-10-12. [MEASUREMENTS.md](MEASUREMENTS.md)의 실제 외부 API 관측을 근거로 다섯 가지 판단을 정리했다. 각 항목은 선택·이유·반대 장점·틀리는 상황으로 구성한다. 선택값은 현재 구현과 사용자가 유지하기로 확인한 기본 정책이며, 실측 최적값을 입증하지 못한 항목은 한계를 남긴다. 퇴사·조회 실행 시점·보관·본인 수정의 기존 업무 정책은[별도 문서](BUSINESS_DECISIONS.md)에 보존했다.

MEASUREMENTS에는 표본·통계·측정 한계·설정 근거를, 이 문서에는 **선택·이유·반대 장점·틀리는 상황**을 짧게 기록한다. 연결5초와 폴링5초·120초·24회는 정량 실측 근거가 부족한 현재 보호 설정이며, 아래 이유를 실측으로 해당 숫자를 도출했다는 주장으로 확대하지 않는다.

## 1. 타임아웃

- **선택:** 연결5초·본문 수신까지 전체 요청30초로 제한한다.
- **이유:** 정상 LIST 최대27.108초(n=3)를 수용한다. 연결 실측n=0으로5초는 기존 실험 조건을 유지했다.
- **반대 장점:** 60초는 더 늦은 정상 응답을 수용하고, 짧은 제한은 실패 시 대기를 줄인다.
- **틀리는 상황:** 연결 환경이 바뀌거나30초 넘는 정상 응답이 늘면 재측정해야 한다. DETAIL에 최적인 값은 미확인이다.

[실측·선택 근거](MEASUREMENTS.md#71-타임아웃).

## 2. GET 재시도와 간격

- **선택:** 추가 재시도0회로 두며 간격은 사용하지 않는다. 후속 호출은 유효 대기 안내를 준수한다.
- **이유:** 실제 retry n=1에서503→30초 대기→500으로 회복0/1이었다. 개선 근거 없이 호출을 늘리지 않는다.
- **반대 장점:** 제한된 재시도는 일시 장애를 자동 회복할 가능성이 있다.
- **틀리는 상황:** 추가 실측에서 회복 효과가 확인되면0회 정책은 불필요한 수동 작업을 만든다. 장기 회복률0%로 단정하지 않는다.

[실측·선택 근거](MEASUREMENTS.md#72-재시도-횟수와-간격). Fixed/Exponential 비교 n=0이다. 코드의 Fixed1초는 비활성 지원값이며 현재 사용되는 간격이 아니다.

## 3. 폴링과 중단

- **선택:** 응답 후5초, 예약부터120초·최대24회. 최종 상태·오류·예산 초과에서 중단한다.
- **이유:** 정확한 완료시간 n=0·자동 최종 발견 n=0이어서 최적 주기 대신 호출 빈도·관찰 상한을 정했다.
- **반대 장점:** 짧은 주기는 발견을 앞당기고 긴 주기는 GET 수를 줄일 수 있다.
- **틀리는 상황:** 처리가120초보다 오래 걸리면 자동 관찰이 먼저 끝난다. 수동 발견88.872002초(n=1)를 순수 완료시간으로 보지 않는다.

[주기 선택](MEASUREMENTS.md#73-폴링-주기)·[중단 조건](MEASUREMENTS.md#74-재시도폴링을-중단하는-조건). 5초·120초·24회는 자원 관리 선택이며 실측 최적값 검증은 미완료다.

## 4. 중복 POST와 결과 불명

- **선택:** POST는 재시도하지 않는다. 중복 요청을 로컬에서 억제하고 결과 불명은 관리자 대조로 처리한다.
- **이유:** 반복 비교2쌍 모두 다른checkId였다. 외부 멱등성을 가정할 수 없고 실제 timeout 복구 n=0이다.
- **반대 장점:** 재전송하면 실제 미생성 요청을 빠르게 다시 처리할 수 있다.
- **틀리는 상황:** 대조 가능한 기록이 없으면 결과 불명이 남는다. 로컬 제어만으로 외부 exactly-once를 보장하지 않는다.

[반복 POST 실측](MEASUREMENTS.md#3-같은-employeeid로-post를-반복한-결과). 최소 재조회 간격·결과 유효기간은 이 실측으로 정할 수 없어 임의의 기간을 붙이지 않았다.

## 5. 동시 요청 상한

- **선택:** 업무 외부 호출을 애플리케이션 인스턴스당1로 제한한다.
- **이유:** 후속 동시성1은 n=3 중503 1건 후 중단했고2·3은 각각n=0이다. 초기 비교도 시각·표본이 달라 안전 상한을 증명하지 못했다.
- **반대 장점:** 상한을 높이면 병렬 처리로 처리량을 늘릴 가능성이 있다.
- **틀리는 상황:** 처리량이 커지면1이 병목이 될 수 있고 다중 인스턴스에서는 전체 호출 수를1로 보장하지 못한다.

[동시성 실측](MEASUREMENTS.md#5-동시-요청-수를-늘렸을-때의-변화). 실험 도구의 중단을 API가 동시성2·3을 거부한 것으로 해석하지 않았다.

## 근거와 적용 범위

원본은 고유39실행·65시도이며[실행 인덱스](measurements/integrated/INDEX.md)에서 추적한다. timeout·재시도·폴링의 실제 설정명은[MEASUREMENTS 부록](MEASUREMENTS.md#부록-코드-설정과-원본-추적), 후보 비교 모형과 추가 검증은[설정 근거](API_DECISION_EVIDENCE.md)에 있다. 이번 문서 변경은 판단 내용을 실측과 연결한 것이며 코드·운영 변수·원본 데이터를 변경하지 않았다.
