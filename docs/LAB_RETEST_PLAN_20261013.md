# 배포 브라우저 재실행 계획 — 2026-10-13

상태: **핵심 최대44 HTTP·POST3건 실행 승인 / B01 오류로 재실행 중단**. 사용자는 전체 계획 확인 후 “직접 실행해줘”라고 요청했다. 실제 외부 호출은 GET2건·POST0건이며 미사용 전체 예산은42건이다. 첫 오류 중단 조건에 따라 나머지 케이스·확장93건·기존1100건은 실행하지 않았다. 기존 데이터39run/65시도는 유지하고, 재실행은 새 날짜·실행ID로 분리한다.

## 브라우저 확인

Railway 배포 탭을 열었고 API Reliability Lab으로 이동할 때 로그인 화면으로 돌아왔다. 이후 사용자가 재로그인했고 관리자 표시와 Lab 화면 진입을 확인했다. 기존 저장 계획 목록 및 후속 케이스 선택 항목을 불러왔다. 키 입력·실행 승인 체크·외부 호출은 하지 않았다. 로그인·포털 화면 요청은 외부 Background Check 호출 예산과 구분한다.

## 추천 범위: 먼저 핵심 44 HTTP / POST 최대 3건

## 기존11조건·각100 HTTP의 처리

이전 초기 계획은 GET의 요청제한10/30/60초×동시성1/2/3, 생성폴링, 중복POST의11조건이다. 조건당100 HTTP·총1100 HTTP 목표와 기존 관측을 지우거나 덮어쓰지 않는다.

현재 저장된 기본 캠페인 버튼은 정상 종료 후 다음 차수를 자동 실행한다. 따라서 이를 누르고 임의 시점에 멈추는 방식으로44건 상한을 보장하지 않는다. 위 추천안은 예산이 정해진 후속 계획과 단일 중복 실험을 사용한다. **11조건·각100건을 다시 시작하려면 별도 대규모 계획과 POST 상한을 검토·확인한다.** 이번137건 검토안에1100건을 포함하지 않는다.

## 공통 조건·대상·저장

- URL: https://internal-employee-portal-production.up.railway.app/
- 외부 서버·경로·X-Candidate-Key 헤더는 첨부 Swagger와 공통 Client를 따른다. 키는 사용자가 앞서 허용한 입력 방식을 사용하며 소스·파일·서버 저장 결과에 쓰지 않는다.
- GET은 등록된 과제 시드 EMP-001을 기준으로 한다. DETAIL은 같은 키·사번의 기존 조회ID를 확인한다. 호출 전까지 실제 유효성을 확정하지 않으며 실패를 기록한다.
- P02 대체 시 과제 시드 EMP-002(성김/이름민준/1994-11-02), 중복 실험은 EMP-001(성김/이름민준/1990-03-15)의 가상 데이터를 사용한다. P04는 별도 신규 조회3건의 입력과 대상도 실행 전에 확인한다. 생성된 외부 기록은 삭제하지 않는다.
- 연결5초, 일반 요청30초(T01은60초), 실행별 전체120초, 묶음/반복 후2초 대기, 단계별 동시성최대3을 유지한다. R04의 후속60초·대기10초는 별도 프로토콜이다.
- 503·429·대기 안내 이후 부하 확대를 중단한다. 안내를 짧게 잘라 호출하지 않는다. C03 및 허용한 retry 실험 외에는500에서도 종료한다. 명시적으로 이미 시작한 요청의 결과는 저장하고, 후속 요청은 추가하지 않는다.
- 키·개인정보·상세 응답을 저장하지 않고 실행ID·조건·실제 시도·지연·HTTP·상태 관측·대기·중단 이유만 남긴다. LAB_RECORDING_ENABLED가 실제 활성인지 화면과 서버 저장 목록으로 확인한 후 실행한다. 단일 실험도 recording 활성 시 lab_runs에 저장되는 기존 구현을 사용한다.
- 승인 예산은 이번 재실행에만 적용하며 이전130 HTTP 예산을 자동 재사용하지 않는다. 최초요청·retry·polling·목록대조·timeout·취소를 모두 실제 시작 시도에 포함한다. 포털의 로그인·저장 조회는 외부 호출 수와 구분한다.
- N01 연결 재사용 계측과P05 창 간 동일 조회 연결은 현재 화면에 실행 기능이 없어 이번 범위에서 제외한다. 따라서 연결 단계5초의 정량 근거가 이 재실행으로 반드시 해결된다고 약속하지 않는다.
