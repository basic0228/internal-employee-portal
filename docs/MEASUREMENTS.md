# MEASUREMENTS.md — API 실측 결과

기준일: 2026-10-12. 이 문서는 **첨부 외부 API가 실제로 반환한 응답·상태·지연과, 그 관측에 따라 선택한 호출 정책**을 다룬다. 과제 제출물2의 항목 순서로 작성했다. 이번 문서 작성에서 추가 외부 호출·운영 설정 변경은 없었으며, 원본에 없는 수치나 성공률을 만들지 않았다.

**최종 선택값:** 연결 timeout 5초, 전체 요청 timeout 30초, GET·POST 추가 재시도 0회, 폴링 응답 후 5초·예약부터 120초·최대 24회, 업무 HTTP 동시성 인스턴스당 1. [선택 이유](#7-실측을-근거로-선택한-설정과-이유)는 7절에 있다.

## 측정 조건·표본·계산 방법

관리자 브라우저/스크립트 → Railway 서버 → 공통 BackgroundCheckClient → 외부 API 경로로 호출했다. Java 21/JDK HttpClient HTTP/1.1을 사용했다. 서버 monotonic clock의 `elapsedMs`는 외부 요청 경과시간이며 PC↔포털 왕복·큐 대기·업무 처리시간과 구분한다. 연결 단계 시간과 물리적 연결 재사용 여부는 별도 계측하지 않았다.

| 측정 집단 | 실행 n | 실제 HTTP 시도 n | 응답 수신 완료 n | POST n |
|---|---:|---:|---:|---:|
| 초기 11조건 | 15 | 34 | 31 | 6 |
| 후속 130 HTTP 예산 실행군 | 13 | 18 | 16 | 2 |
| 별도 탐색 | 11 | 13 | 8 | 0 |
| 기록 재고 합계 | 39 | 65 | 55 | 8 |

runId/attemptId의 중복을 제거한 고유 39실행·65시도다. 초기 조건마다 100건을 목표로 했으나 실제 34건/목표 1100건으로 1066건은 미시행이다. 오류·대기 안내에 따라 중단했으며 미시행을 실패나 성공으로 집계하지 않았다. 후속 업무 화면 검증의 5외부호출은 지연 계측 원본이 없어 위 65시도·Excel에 합산하지 않는다.

백분위수는 **Type7** 보간이다. 정렬값 `x[0..n−1]`, `h=(n−1)p`, `j=floor(h)`, `a=h−j`일 때 `Q(p)=x[j]+a×(x[min(j+1,n−1)]−x[j])`로 계산했다. 평균은 합/n, p50은 중앙값이다. 소표본 p99는 관측값 사이의 보간이며 장기 tail을 보장하지 않는다. 오류 후 중단한 탐색 표본을 무작위·독립 동일분포로 가정하지 않았다. 아래 비율은 관측 표본의 비율이며 서비스의 장기 장애 확률이 아니다.

## 1. GET /background-checks/{checkId} 응답 지연

**상세 GET(DETAIL)을 직원별 목록 GET(LIST)과 분리했다.** 응답 본문 수신을 완료한 정상·오류 응답을 따로 계산했다. 단위는 ms다.

| 응답군 | 표본 n | p50 | p95 | p99 | 최댓값 | 측정 실행 ID |
|---|---:|---:|---:|---:|---:|---|
| HTTP 200 정상 DETAIL | 2 | 325.184 | 332.955 | 333.645 | 333.818 | fa48a462-cfff-4b10-9259-5b1eb2d89365 |
| HTTP 500 오류 DETAIL | 1 | 229.141 | 229.141 | 229.141 | 229.141 | a42e5d55-0aa3-4a75-9f70-418a803de39d |

별도 DETAIL timeout은 2건이다. 첫 실행의 중단 경과 30,003.720794ms(n=1), 후속 P02 `4ff4f593-c904-4916-a2da-937217b90c98`의 중단 경과 30,001.117693ms(n=1)였다. 완료 응답 지연이 아니므로 위 백분위수에 넣지 않았다. DETAIL은 총 5시도·완료 3·timeout 2다.

정상 2건은 같은 run의 pending 응답이다. 평균·중앙값은 각각 325.184ms(n=2)로 같지만 두 값의 산술적 특성이므로 분포가 대칭이라는 증거는 아니다. 이후 업무 화면에서 clear/flagged DETAIL을 각각 1건 확인했으나 요청 지연을 계측하지 않아 표에 추가하지 않았다. 정상 n=2만으로 짧은 timeout을 정하기에는 timeout 2건과 표본 불확실성이 남는다.

## 2. HTTP 상태코드 분포

분모는 **외부 API 응답 수신 완료 n=55**다. 포털 로그인·권한 API의401/403, 로컬 모의 API 응답은 이 분포에 포함하지 않는다. HTTP 헤더만 관측한 전송 중단을 완료 응답으로 세지 않는다.

| 상태코드 | 건수 | 비율 | 분모 n |
|---|---:|---:|---:|
| 200 | 18 | 32.73% | 55 |
| 201 | 8 | 14.55% | 55 |
| 500 | 18 | 32.73% | 55 |
| 503 | 11 | 20.00% | 55 |

별도 전송 결과는 요청 timeout 8/실제 65시도(12.31%), 취소 2/65(3.08%)다. timeout은 설정 시간 안에 관찰을 완료하지 못한 결과이며, 외부 서버·통신망·클라이언트 중 어느 원인인지 분리하지 못했다. 취소는 테스트 도구 측에서 관찰을 중단한 표본으로 외부 API가 반환한 오류가 아니다. CONNECT_TIMEOUT·NETWORK_ERROR 관측은 각각0/65이며 연결 단계별 계측은 미수행이다. timeout을 HTTP408·504로 추정하지 않았다.

서로 다른 조건·시각을 합친 전체 55건은 기록 검산용이다. 동일 조건의 장기 오류율로 해석하지 않는다.

## 3. 같은 employeeId로 POST를 반복한 결과

초기 E11에서 같은 employeeId의 POST를 두 번씩 비교했다. **비교 n=2쌍(POST 4건), 두 쌍 모두 서로 다른 checkId를 반환했다(2/2쌍).**

| 실행 ID | 두 POST의 반환 ID | 후속 직원 이력 GET 대조 | 비교 표본 n |
|---|---|---|---:|
| 6389a638-6cb5-42c5-9cd0-4170c34ed323 | 서로 다름 | 신규 이력 2건 확인 | 1쌍 |
| da9e2620-c41a-4997-a4eb-9403b35dd6df | 서로 다름 | LIST 실패로 대조 미확인 | 1쌍 |

이력 대조 성공은 1/2쌍이다. 같은 employeeId의 POST가 외부에서 멱등 처리된다고 가정할 수 없다. 목록 차이만으로 응답 유실 POST의 생성 여부나 다른 호출자의 개입까지 증명할 수도 없다. **실제 POST timeout 뒤 원격 생성·복구 검증 n=0**이며 로컬 모의 복구 성공을 외부 성공률로 쓰지 않았다.

외부 API의 재전송 안전성을 확인하지 못했으므로 POST 추가 재시도0회를 선택했다. 이표본은 외부 API가 반복 생성한 결과다. 우리앱의 중복 제어·이력 저장 검증은 포함하지 않았으며, 해당 설계는[DECISIONS](DECISIONS.md)와[업무 정책](BACKGROUND_CHECK_POLICY.md)에 기록했다.

## 4. pending에서 최종 상태까지 걸린 시간

| 관찰 범위 | 표본·결과 | 시간 해석 |
|---|---|---|
| Lab POST 8건 | 즉시 clear 4·초기 pending 4. pending 최종 발견 n=0 | pending 4건은 오류·timeout으로 관찰이 끝나 중도절단. 완료시간 계산 불가 |
| 후속 업무 EMP-001 | 즉시 clear n=1 | pending 전환 표본에 포함하지 않음 |
| 후속 업무 EMP-002 | pending→수동 flagged 발견 n=1, 자동 최종 발견 n=0 | 아래 관찰 경과만 계산 가능 |
| 정확한 서버 업무 처리시간 | 유효 표본 n=0 | 서버 createdAt 미수집·시계 동기화 미측정으로 미확인 |

EMP-002 최초 pending 관찰은 `2026-10-11T22:28:27.848217Z`, 자동 확인 중단 관찰은 `22:28:34.219924Z`, 수동 최종 관찰은 `22:29:56.720219Z`다. **최초 pending→수동 최종 발견의 앱 시각 차이는 88.872002초(n=1)**다. 수동 대기·자동 중단·HTTP 시간을 포함하므로 순수 업무 완료시간이나 정확한 발견 지연으로 쓰지 않았다. 서버 표시 완료시각 `22:28:58.774Z`와 앱 시각의 차이도 시계 동기화를 확인하지 않아 정확한 발견 지연으로 확정하지 않았다.

이 보충 관찰의 실제 외부 호출은 POST1·자동 GET1·수동 GET1·retry0, 합계3건이다. 외부 pending과 최종 flagged 응답을 관찰했지만 자동 중단의 HTTP 코드·전송 결과는 계측 원본이 없어 추정하지 않는다. 앞선 EMP-001의 POST1·수동 GET1을 합친5외부호출은 포털을 경유한 보충 관찰이며 Lab 지연 표본과 별도다. [보충 관찰 증빙](measurements/business-validation.json)에 시각·상태·호출 수를 기록했다.

## 5. 동시 요청 수를 늘렸을 때의 변화

초기 동시성 실험은 **목록 GET(LIST)** 으로 수행했다. 연결 제한 5초·호출 간격 2초는 공통이며 요청 제한 10/30/60초와 동시성 1/2/3을 구분했다. 시행 시각·표본 수·오류 중단이 달라 통제된 인과 비교는 아니다. 정상 응답 지연 단위는 ms다.

HTTP200=2(14,970.565688 / 15,390.091008ms), HTTP503=1(218.234213ms·본문30초 안내)이었다. 정상p50=15,180.328348·p95=15,369.114742·p99=15,385.895755·최대15,390.091008ms(n=2)다. 503 이후 테스트 도구가 후속 묶음을 중단해 동시성2·3은 각각n=0이다. 이 중단은 우리 측 실험 제어이며, API가 동시성2·3을 거부했다는 관측은 아니다. **외부 API의 안전한 최대 동시성은 현재 자료로 확정하지 못했다.**

## 6. swagger.yaml과 실제 동작 대조

명세 버전은 1.1.1이며 SHA256은 `30e38d5a486238827407063b4ca549e67b5f046c8ad40e560d45a1729eb86d24`다. 원본의 specSha256과 일치했다. 완료 응답의 구현된 검사 issue는 0/55지만 명세 모든 분기를 검증했다는 뜻은 아니다.

### 6.1 명세에 있으나 실제로 확인하지 못한 것

- 외부 401·404 전용 실험 n=0, 완료 HTTP 55건에서 관측 각각 0건. 해당 분기가 잘못됐다고 판단하지 않는다.
- 유효한 표준 Retry-After 헤더 관측은 0/완료 55건. 명세의 헤더 분기 실제 검증은 남아 있다.
- estimatedCompletionSeconds의 정확성을 평가할 서버 업무 처리시간 표본 n=0. 추정값과 실제 완료시간의 일치도를 판단하지 못했다.

### 6.2 명세에 설명되지 않았으나 호출에서 발견한 것

- 같은 employeeId 반복 POST의 비교2쌍 모두 별도checkId를 반환했다. 명세는 반복 요청의 멱등성·중복 생성 정책을 보장하지 않는다.
- 정상 LIST가 26,884.973ms(E09 정상 n=2의 최대), 27,108.368ms(E11 정상 n=3의 최대)까지 걸렸다. 명세는 지연 분포나 응답시간 상한을 제공하지 않는다.

timeout8·취소2/실제65시도는2절의 클라이언트 관찰 결과로 별도 기록했다. 이값들을 명세 외 HTTP 응답이나 외부 API의 내부 동작으로 단정하지 않는다.

명세에 있는 500·503은 각각 18·11건/완료 55건 관측했다. 본문 retryAfter는 9/55건에서 관측했고 모두 30초였다. 본문 안내와 POST의 즉시 clear는 명세가 허용하므로 명세 외 현상으로 분류하지 않았다.

### 6.3 명세의 값이 실제 상황에 맞지 않는다고 판단했는가

**독립적인 명세 위반이나 비현실적인 값을 입증하지 못했다.** 예시 estimatedCompletionSeconds=20초와 Retry-After=30초를 항상 성립하는 SLA·고정 폴링 주기로 사용하지 않았다. 정확한 업무시간 n=0이라 20초 추정값의 정확도를 평가할 수 없다. 실제 R02는 30초 대기 후에도 500으로 회복 0/1이었으며 대기 안내를 회복 보장과 구분했다. 오류 본문의 선택 필드는 명세에 required가 없어 존재할 때만 검사했다. 외부 500의 내부 원인은 제공자 로그가 없어 규명하지 못했다.

## 7. 실측을 근거로 선택한 설정과 이유

아래는 **이번 제출에서 선택·코드 반영한 값**이다. 사용자는 운영 검증 때 기본 정책 유지를 확인했다. ‘일반적으로 권장되는 값’을 근거로 사용하지 않았다. 실측으로 특정 숫자를 도출할 수 없었던 항목은 자원 관리 선택과 검증 한계를 명시한다.

### 7.1 타임아웃

| 대상 | 선택값 | 실측 근거·표본 n | 왜 이 값인가 |
|---|---|---|---|
| 연결 | 5,000ms | 연결 단계 분리 실측 n=0. 실험 연결 제한 5초 | 실험 조건을 유지하며 연결 대기를 제한했다. 응답 p99에서 도출한 최적값은 아니며 연결시간의 근거는 부족하다 |
| 전체 요청 | 30,000ms | E09 LIST 정상 n=2 최대26,884.973ms, E11 정상 n=3 최대27,108.368ms. DETAIL 정상 n=2와 timeout 2건은 별도 | 10초는 관측된 느린 정상을 놓쳐 30초를 선택했다. 약27초 정상을 수용하면서 60초 후보보다 실패 시 대기 상한을 줄인다. DETAIL 특화 최적값·30초 이후 회복은 미검증 |

전체 요청 제한은 JDK Client의 본문 수신을 포함한 deadline이다. 별도 socket read idle timeout을 설정한 것은 아니다. 연결 5초는 전체 30초 안의 제한이며 35초로 더하지 않는다.

### 7.2 재시도 횟수와 간격

**GET 추가 0회·POST 항상 0회**를 선택했다. 재시도와 pending 결과를 확인하는 별도 GET 폴링은 구분한다.

- GET: R02 `c4e7adbc-a862-4e9a-911f-fd4821d87ec7`의 실제 추가 retry n=1에서 503→본문 30초 안내→실제 30,000.376680ms 대기→500이었다. 회복 0/1로 개선 근거가 부족해 추가 부하를 발생시키지 않는다. 장기 회복률이 0%라고 확정한 것은 아니다.
- POST: 반복 비교 2쌍 모두 별도 ID였고 실제 timeout 복구 n=0이어서 응답 유실 시 중복 생성을 피하려고 자동 재전송을 금지했다.
- 간격: 현재 재시도 0회이므로 실제로 사용하는 재시도 간격은 없다. 코드의 Fixed 1,000ms는 비활성 지원값이다. Fixed/Exponential 실제 비교 n=0이어서 성공률·우열을 가정하지 않았다. 추후 활성화 지원은 GET 500/503만 추가 최대1회다.
- 대기 안내: 유효 Retry-After 헤더 우선, 없으면 본문retryAfter를 사용한다. 후속 호출을 허용할 때는 안내 시간을 준수하고, 다음 요청 예산이 부족하면 안내를 줄여 호출하지 않는다. 헤더 분기 관측은0/완료55건이며 본문30초 안내9/55건과구분한다.

### 7.3 폴링 주기

**응답 후 5초 / 예약부터 120초 / 자동 GET 최대24회**를 선택했다. Lab 최종 발견 n=0·업무 수동 발견 n=1·자동 발견 n=0·정확한 서버 업무시간 n=0이라 완료시간 분포로 최적 주기를 산출할 수 없었다.

5초는 응답 후 대기를 두어 연속 즉시 호출을 막는 선택이다. 120초는 POST 시간을 포함한 자동 관찰 예산이며 24회는 별도 호출 상한이다. `120초/5초=24`는 공학적 상한 비교이며 실측 평균 완료시간이나 실제24회 보장이 아니다. HTTP 시간·오류·대기 안내 때문에 실제 호출은 더 적을 수 있다. 자동 GET은 남은 예산과 요청30초 중 작은 제한을 사용한다. 업무88.872002초(n=1)를 순수 완료시간으로 대입하지 않았다.

짧은 주기는 발견 지연을 줄일 수 있고 긴 주기는 GET 수를 줄일 수 있다. 현재 자료로 2/5/10초의 우열·120초 내 완료 보장을 확정하지 못했다. 따라서 이 값은 완료시간의 최적 추정이 아닌 자원 상한이며 추가 완료시간 실험이 필요하다.

### 7.4 재시도·폴링을 중단하는 조건

- 현재 GET·POST는 추가0회이므로 첫 시도 뒤 자동 재전송하지 않는다.
- GET 지원 경로를 활성화하더라도 500/503 이외, timeout·전송 오류·잘못된 대기 헤더·대기 후 다음 전체 요청 예산 부족·스레드 중단에서는 추가 시도하지 않는다.
- 자동 폴링은 clear/flagged, HTTP 오류·timeout·네트워크 오류·응답 계약 불일치, 잘못된/과도한 대기 안내,120초·24회 상한 또는 다음 관찰 시각이 마감 이후이면 중단한다.
- 관찰이 중단된 pending을 최종 완료나 특이사항 없음으로 해석하지 않는다. POST 응답 유실·목록 대조 실패·빈 목록만으로 미생성을 확정하지 않는다.

실측 중 500·503과 timeout을 관측했고 반복 POST의 외부 멱등성이 확인되지 않았으며 retry 회복도 0/1이었다는 사실을 반영했다. 자동 최종 발견·실제 POST timeout 복구·장기 운영 효과는 미검증으로 남긴다.
