### 계산 방법

같은 조건과 Endpoint에서 완료된 HTTP 지연을 오름차순 `x[0]…x[n−1]`로 놓고 Type 7을 사용한다. `h=(n−1)p`, `j=floor(h)`, `a=h−j`이면 `Q(p)=x[j]+a(x[min(j+1,n−1)]−x[j])`다. 평균은 합/n, p50은 중앙값이다. `n=0`은 TODO, `n=1`은 동일 관측을 반복 표시한다. 반올림은 표시할 때만 한다. [R 공식 quantile 문서](https://www.stat.ethz.ch/R-manual/R-devel/library/stats/html/quantile.html).

### Tail latency, 작은 표본, 중단 편향

E11의 정상 LIST n=3은 평균 9,474.18ms, 중앙값 780.45ms, 차이 8,693.72ms, 최댓값/중앙값 34.73배다. 낮은 중앙값만으로 약27초의 성공 응답을 설명할 수 없다. 반면 이 3건에서 미래 p99나 이상치 발생률을 확정할 수도 없다. 이상치 후보도 삭제하지 않고 원본에 남긴다. 소표본 IQR 판정에서 이상치가 없더라도 tail이 없다는 근거로 쓰지 않는다.

표본의 순위 간격은 대략 1/n이다. 상위 백분위수는 작은 n에서 최상위 한두 값의 보간에 좌우된다. 독립 동일분포를 **가정한 수학 예시**에서 참 p99를 넘는 값이 한 번 이상 나타날 확률은 `1−0.99^n`이다. n=100에서도 약63.40%, n=299에서는 약95.05%다. 이는 이번 실험의 신뢰구간이나 권장 호출 수가 아니며, n=100을 품질 보증 기준으로 삼지 않는다.

오류를 만나는 즉시 중단했으므로 표본 크기와 종료 시점이 결과에 의존한다. 조건들을 다른 시각에 실행했고 일부는 성공 묶음 뒤 오류 묶음이 이어졌다. 따라서 500 비율의 단순 차이로 동시성의 인과 효과를 판단하거나, 독립 고정 표본을 가정한 검정·신뢰구간을 운영 오류 확률처럼 제시하지 않는다.

완료 관측만 사용한 ECDF `F̂(t)=Σ1(Tᵢ≤t)/n`도 '완료 응답을 얻은 표본'에 조건부다. 긴 요청의 타임아웃·다른 요청의 실패로 취소된 요청이 빠져 있어 전체 성공 지연을 낙관적으로 볼 수 있다.

## 5. Retry·Backoff·Retry-After

500 n=11, 503 n=4는 재시도 대상을 검토할 입력이며 회복을 관측한 retry 실험이 아니다. 애플리케이션 retryIndex는 전체34건에서 0이다. 성공률, 성공까지의 기대 횟수, 기하분포에 따른 성공 확률은 TODO다.

GET은 HTTP 멱등성과 업무상 읽기 동작을 확인한 후 재시도를 검토한다. POST는 외부 중복 생성을 관측했으므로 응답 불명 시 자동 재전송하는 초안으로 만들지 않는다. HTTP 표준도 비멱등 요청의 자동 재시도에는 조건을 둔다. [RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2).

추가 retry 횟수 R, 요청당 상한 T, 대기 bᵢ라면 스케줄러 등의 여유를 제외한 미절단 상한은 `W=(R+1)T+Σbᵢ`다. Fixed는 b, Exponential은 `min(cap,b×2^(i−1))`다. 대기 안내 h를 채택할 때는 `max(bᵢ,hᵢ)`로 계산한다.

다음은 **공학 모델**이며 실측 성공률이 아니다. T=30초, b=1초, cap=4초, 전체 deadline D=120초를 가정한다. 본문 30초 안내를 관측한 503은 2건, 표준 Retry-After 헤더 관측은 0건이었다.

| 추가 R | HTTP 시도 최대 | 안내 없는 Fixed W | 안내 없는 Exponential W | 매 대기 h=30초 가정 W | D=120초와 관계 |
|---:|---:|---:|---:|---:|---|
| 0 | 1 | 30초 | 30초 | 30초 | 예산 이내 |
| 1 | 2 | 61초 | 61초 | 90초 | 예산 이내 |
| 2 | 3 | 92초 | 93초 | 150초 | 모든 시도가 들어갈 보장 없음 |

전체 deadline이 시간을 자르면 `min(D,W)`는 처리 종료 상한이며 모든 시도의 완료 보장이 아니다. 본문 30초는 향후 안내의 상한이 아니다. Retry-After 표준 형식은 초 또는 HTTP 날짜이므로 헤더 파싱, 잘못된 값, 날짜의 시계 차이도 고려한다. 본문 fallback은 API 고유의 호환안으로 구분한다. [RFC 9110 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3).

**검토 초안:** GET의 500/503은 횟수 제한을 둔 대상 후보다. 헤더 우선, 본문 fallback을 검토하고 필요한 대기와 다음 시도가 잔여 예산에 들어가지 않으면 중단한다. 401·404·429는 이번 n=0이므로 실측 완료로 표시하지 않는다. 인증·입력 등을 수정하지 않은 재시도는 피하는 방향으로 별도 확정한다. 연속 오류, 관리자 중지, deadline, 호출 예산 소진도 중단 조건 후보다. R=0은 부하 최소, R=1/2는 회복 기회가 늘지만 최대 호출 수는 R+1배다. Jitter 효과와 회복 확률은 미측정이다.

## 6. Polling 후보 비교

POST6건은 초기 clear4건·pending2건이다. clear로 반환된4건은 이미 최종 상태를 관측했으므로 추가 polling을 생략할 수 있지만 정확한 업무 완료시간이 0ms라는 뜻은 아니다. completedAt이 없는 관측에 HTTP 시간을 넣지 않는다.

E10의 최초·마지막 pending 관측 시각 차이는 10,780.12ms(n=1구간)다. 이는 서버 응답 관측의 시각 차이며 정확한 업무 완료시간이 아니다. 다음 DETAIL GET가 timeout으로 끝났으므로 종료까지 약46초인 실험도 업무 완료시간으로 부르지 않는다. 응답 후 다음 GET 시작까지의 실측 대기는 약5,006.75 / 5,123.00 / 5,048.60ms(n=3구간)다. P=5,000ms는 실제 시작 간격이 항상5초라는 뜻이 아니다.

이상적 모델에서 정확한 완료시각 d와 일정 간격 P가 알려졌다면 `N=ceil(d/P)`, 발견 지연은 `NP−d`로 0이상 P미만이다. 평균 P/2는 완료 위상이 균일하다는 추가 가정이 필요하며 이번 실측 추정으로 표시하지 않는다. d의 표본 n=0이므로 N·지연의 수치 비교는 TODO다.

실제 구현은 응답 후 기다리므로 시작 간격은 대략 HTTP시간 L+P다. POST1건, 최대 K회 GET의 상한 모델은 `W=Tpost+K(P+Tget)`다. Tpost=Tget=30초, K=5, D=120초라는 **가정**에서 다음과 같다.

| P후보 | K | 절단 전 W | 예상 GET수·발견 지연 | 해석 |
|---:|---:|---:|---|---|
| 2초 | 5 | 190초 | TODO, d표본n=0 | 대기는 짧지만 호출 빈도 증가 |
| 5초 | 5 | 205초 | TODO, d표본n=0 | 현재 실험 조건과 같음 |
| 10초 | 5 | 230초 | TODO, d표본n=0 | GET를 줄일 수 있으나 발견 지연 가능 |

모두 120초 안에 GET5회가 끝날 보장은 없다. **검토 초안:** clear/flagged에서 종료하고 입력·인증 오류, 사용자 중지, 전체 deadline·예산 도달 시 중단한다. pending이나 결과 불명을 clear로 처리하지 않는다. 상한 연장의 장점은 결과 발견 기회, 단점은 자원 점유와 대기 증가다. flagged, 정상 pending→최종 상태, 장기 pending은 추가 검증이 필요하다.

## 7. 동시성과 500의 판단

동시성 비교는 E01–E09의21시도에 한정한다. 각 조건의 평균·p95·상태 건수는 앞 표와 엑셀에 있다. GET대상·Client revision·연결 상한은 공통이지만 실행 시각, 요청 상한, 실제 표본수, 응답군, 중단 조건의 영향이 다르다. 30초 조건은 동시성1·3에서503, 2에서500이었다. 60초 조건은 1·3에서 약30.54초의503, 2에서 빠른500을 관측했다. 동시성 증가에 따른 단조로운 악화를 증명하지 않는다.

Little의 관계식 `L=λW`는 같은 시스템·모집단·기간의 평균과 안정적인 유입/처리를 확인하고 적용해야 한다. [MIT 대기행렬 강의 자료](https://web.mit.edu/6.263/www/l6.pdf). 이번에는 λ를 정상상태에서 계측하지 않았다. 평균 지연만으로 안전한 동시수나 처리 능력을 역산하지 않는다. C×T는 요청 슬롯 점유를 생각하는 보수적 자원 예산이며 성능 최적화의 증명이 아니다.

500은11건 모두 외부에서 HTTP로 반환된 관측이며 응답 크기는119bytes, 지연은213.20~1,194.10ms다. 클라이언트 timeout·로컬500과 구분할 수 있지만 외부 내부 예외 원인은 불명이다. 본문·외부 request ID는 저장하지 않아 크기 일치만으로 같은 내부 예외라고 단정하지 않는다. LIST에는 선행POST가 필수라고 명시되지 않았으며 E07–E09에도200이 있다. DETAIL에는 유효 checkId가 필요하며 POST반환ID 등을 사용한다.

**검토 초안:** 동시성1은 일시적 부하 보호 후보다. 2/3채택 전 동일 조건의 시간 블록을 번갈아 비교하고 중단도 저장한다. 500조사에는 키/개인정보를 제외한 request ID, 허용한 오류 분류, 제공처 로그 대조가 도움이 된다. 현재 입력 오류·선행 조건 부족·부하 장애 중 하나로 확정하지 않는다.
