## 변경과 사용

기존 관리자 단일 Lab의 캠페인 영역에 후속 계획 선택을 추가했다. 계획 저장은 API를 호출하지 않는다. 한 절차에 키·가상 대상을 입력하고 확인 체크 후 실행한다. 키와 실제 대상은 저장하지 않으며 기존 lab_campaigns/lab_runs에 정제 메타데이터를 자동 저장한다. 추가 SQL 또는 환경변수는 없다.

|---|---:|---|
| B01 | 3 | 정상 LIST와 계약 확인 |

후속 계획은 절차를 한 번 실행한 뒤 종료한다. 정상 초기 응답이면 남은 retry 예산은 미사용이다. 오류로 일부만 관측한 절차를 자동으로 채우지 않는다. 재실행하려면 검토 후 새 계획을 만든다. C01/C02/R01/R03은 저장한 순서를 검사하고 선행 STOPPED 뒤 다음 비교를 차단한다. 동시성 수준 사이 최소30초 보호 대기도 서버에서 검사한다. 첫 탐색55건을 한꺼번에 자동 실행하는 기능은 없다.

P03은 기존 폴링 시뮬레이터(외부0회)를 사용한다. P05와 N01은 각각 동일 조회 연결 검증·Client 재사용 계측이 선행되어야 하므로 실행 UI를 제공하지 않고 사유를 표시한다.

## 구현 원리

- LabProtocol은 enum과 제한 숫자만 받아 저장한다. 개인정보를 적을 수 있는 자유문자 프로토콜 항목은 없다. 기존 DTO 생성자와 protocol=null인 캠페인을 유지한다.
- LabRunner의 GET_RETRY만 명시적 retry를 허용한다. HTTP/전송 결과와 계약을 검사한 뒤 적격 실패에만 제한 후속 GET을 보낸다. 일반 업무·기존 실험의 중단 규칙은 유지한다.
- Retry-After 헤더 우선/body fallback. 유효 안내를 짧게 자르지 않으며 대기 전후에 다음 요청 전체 제한이 deadline에 들어가는지 확인한다. 미진행은 RETRY_DEFERRED_BUDGET으로 남긴다. POST 자동 retry는 없다.
- logicalOperationId는 초기와 후속을 묶고 retryIndex는 추가 시도의 번호다. 성공률 모델과 실제 회복 표본을 분리한다. 논리 작업 n/초기 적격 실패 n/후속 시작 n/회복 n/미실행 n을 함께 보고한다. 적격 실패 또는 실제 후속 시도 n=0이면 회복 비율은 미확정이다.
- 기존 pending의 실제 checkId는 실행 메모리에서만 사용한다. 서버 보고 업무 시간과 pending→최종 발견 시간을 구분하고, 마지막pending 요청 시작~최초최종 응답 종료의 보수적 구간을 저장한다. 이 구간은 같은 조회·단조 전환 가정이 필요하다.
- 동시성2의3건은2+1 묶음이다. groupWidth와 Client 호출 겹침 최댓값을 기록한다. 외부 wire in-flight·소켓 재사용을 계측했다고 주장하지 않는다.
- 실행별 비교는 정상 지연과 오류를 구분한다. 처리량은 보호 대기·저장 등을 포함한 실행 경과의 정상 응답/초이며 최대 처리능력의 추정이 아니다. 같은 키·대상·환경 확인은 실행자 책임이다.

## C03: 승인된 500 포함 동시성 비교

- 프로토콜 버전2. C03은 LIST/GET_FIXED, DEFAULT/블록1/순서1..3이며 순서와 동시성은 같다. 수준별3건/전체9건/POST0. 서버가 고정 조건·예산·선행 절차 종료·수준 사이30초를 검사한다. 새 SQL 또는 Railway 변수 변경은 필요하지 않다.
- 정상 형식 HTTP500은 오류 표본으로 저장하고 진행한다. `COMPLETED`는 승인된 절차 종료이며 모든 요청 성공을 뜻하지 않는다. retryIndex=0/논리 재시도 작업0. 정상 지연과 실패 건수는 기존 비교 표에서 분리된다.
- 503/429/Retry-After/본문 대기 안내/잘못된 안내/타임아웃/네트워크·계약·저장 오류/사용자 취소는 중단한다. 동시 묶음의 이미 시작한 요청은 기록하며 다음 묶음/수준을 차단한다. ErrorResponse의 선택 필드는 존재할 때만 검사하고 내용을 기록하지 않는다.
