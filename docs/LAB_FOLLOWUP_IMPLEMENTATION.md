## 변경과 사용

기존 관리자 단일 Lab의 캠페인 영역에 후속 계획 선택을 추가했다. 계획 저장은 API를 호출하지 않는다. 한 절차에 키·가상 대상을 입력하고 확인 체크 후 실행한다. 키와 실제 대상은 저장하지 않으며 기존 lab_campaigns/lab_runs에 정제 메타데이터를 자동 저장한다. 추가 SQL 또는 환경변수는 없다.

| 선택 계획 | 최대 HTTP | 실행 목적 |
|---|---:|---|
| B01 | 3 | 정상 LIST와 계약 확인 |
| T01 | 4 | LIST2/최종 DETAIL2, 60초 관찰, 각 요청 독립120초 창 |
| R01 | 12 | 500일 때만 추가1회, 2초/10초 사전 배정, 조건별3작업 |
| R02 | 2 | 503 안내 존중 후 추가1회, 예산 부족 시 생략 |
| P01 | 7 | 기존 pending LIST1/DETAIL≤6, 생성0 |
| P02 | 7 | P01의 별도 승인 대체: POST≤1/DETAIL≤6 |
| C01 | 27 | LIST 동시성 1/2/3 균형3블록 |
| R03 | 18 | 500 추가≤2회, Fixed2·2초/Exponential2·4초 |
| R04 | 2 | GET timeout 후10초 대기/60초 GET1회 |
| P04 | 21 | 간격2/5/10초에 각각 새업무1개, POST≤3 |
| C02 | 27 | 같은 유효 최종 DETAIL의 균형3블록 |

후속 계획은 절차를 한 번 실행한 뒤 종료한다. 정상 초기 응답이면 남은 retry 예산은 미사용이다. 오류로 일부만 관측한 절차를 자동으로 채우지 않는다. 재실행하려면 검토 후 새 계획을 만든다. C01/C02/R01/R03은 저장한 순서를 검사하고 선행 STOPPED 뒤 다음 비교를 차단한다. 동시성 수준 사이 최소30초 보호 대기도 서버에서 검사한다. 첫 탐색55건을 한꺼번에 자동 실행하는 기능은 없다.

P03은 기존 폴링 시뮬레이터(외부0회)를 사용한다. P05와 N01은 각각 동일 조회 연결 검증·Client 재사용 계측이 선행되어야 하므로 실행 UI를 제공하지 않고 사유를 표시한다.

## 구현 원리

- LabProtocol은 enum과 제한 숫자만 받아 저장한다. 개인정보를 적을 수 있는 자유문자 프로토콜 항목은 없다. 기존 DTO 생성자와 protocol=null인 캠페인을 유지한다.
- LabRunner의 GET_RETRY만 명시적 retry를 허용한다. HTTP/전송 결과와 계약을 검사한 뒤 적격 실패에만 제한 후속 GET을 보낸다. 일반 업무·기존 실험의 중단 규칙은 유지한다.
- Retry-After 헤더 우선/body fallback. 유효 안내를 짧게 자르지 않으며 대기 전후에 다음 요청 전체 제한이 deadline에 들어가는지 확인한다. 미진행은 RETRY_DEFERRED_BUDGET으로 남긴다. POST 자동 retry는 없다.
- logicalOperationId는 초기와 후속을 묶고 retryIndex는 추가 시도의 번호다. 성공률 모델과 실제 회복 표본을 분리한다. 논리 작업 n/초기 적격 실패 n/후속 시작 n/회복 n/미실행 n을 함께 보고한다. 적격 실패 또는 실제 후속 시도 n=0이면 회복 비율은 미확정이다.
- 기존 pending의 실제 checkId는 실행 메모리에서만 사용한다. 서버 보고 업무 시간과 pending→최종 발견 시간을 구분하고, 마지막pending 요청 시작~최초최종 응답 종료의 보수적 구간을 저장한다. 이 구간은 같은 조회·단조 전환 가정이 필요하다.
- 동시성2의3건은2+1 묶음이다. groupWidth와 Client 호출 겹침 최댓값을 기록한다. 외부 wire in-flight·소켓 재사용을 계측했다고 주장하지 않는다.
- 실행별 비교는 정상 지연과 오류를 구분한다. 처리량은 보호 대기·저장 등을 포함한 실행 경과의 정상 응답/초이며 최대 처리능력의 추정이 아니다. 같은 키·대상·환경 확인은 실행자 책임이다.

## 검증

- Java21/Maven 전체71개 테스트 통과(후속 Runner13개와 저장 검증2개 추가 포함), package 성공. 루프백 MockBackgroundApi/H2/MockMvc만 사용했다.
- 프런트 통계·계획·내보내기20개 테스트 통과, 기본 및 관리자 opt-in 빌드 성공. 기존500kB 번들 경고는 남아 있다.
- 새 검증: 초기 성공 후 retry0, 500→200/500 지속/500→500→200의 실제 연결, 503 안내 우선·충돌·예산 생략, 401/404/429·계약 오류 중단, pending 없음→POST0, 같은pending→flagged, 즉시 최종POST→GET0, 프로토콜 변조 거절, 대기 중 취소·저장 실패 후 추가 호출0, 후속 절차 재실행 차단, 동시성 선행 순서 차단, 실제 분모와 부분 묶음·정상 지연 분석.
- 가상시계로 모든 deadline 경계를 검증하거나 R04의 실제30초 timeout 회복, 지속pending의6회/120초 중단, N01/P05를 새로 검증한 것은 아니다. 기존 timeout/POST 불명/Client 상한 테스트가 통과했으나 이를 새 외부 정책 성능으로 해석하지 않는다.

외부 API는0회, 운영 DB 데이터 변경은0회다. 기존 데이터와 인증·쿠키·배포 설정은 변경하지 않았다. 운영 브라우저에서 새 계획 저장·실행·다른PC 복구는 배포 후 검증 대상이다.

## 배포 후 실행

1. 배포 완료 후 새로고침하고 관리자 로그인한다. capabilities의 followupProtocolVersion=1 또는 계획 선택 항목으로 새 버전을 확인한다.
2. B01 계획 저장 → 유효한 가상 employeeId와 키 입력 → 조건 확인 → 절차1회 실행. 정상 계약을 확인한 후 T01로 진행한다. 외부 오류 지속 시 동시성을 올리지 않는다.
3. 필요한 가족만 별도 계획으로 실행하고 각 결과를 불러와 논리 작업/관측 n/중단을 검토한다. P02/P04는 실제 외부 POST 기록 생성에 대한 별도 확인이 필요하다.
4. 계획·관측 JSON과 실행별 Markdown을 내보낸다. 최종 정책은 실측과 사용자 확인 후 DECISIONS에 반영한다. 새 retry 원본은 기존 Retry OFF 전용 campaign-evidence 분석 경로에 넣지 않는다.
